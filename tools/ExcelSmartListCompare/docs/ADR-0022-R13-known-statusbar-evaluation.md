# ADR-0022 · R13 상태표시줄 기존 실패를 명시한 평가 후보

상태: 채택 · RC13의 알려진 StatusBar 실패만 명시적으로 수용하는 평가 조건

날짜: 2026-10-03 · 적용: `0.2.0-rc.13`의 정확한 후보 한정

결정 담당: 도구 개발·검증 담당

관련 요구사항·정책: [R13 명세](../../../docs/tools/excel-list-compare/r13-specification.md), [추가 도구 개발 기준](../../../docs/policies/tools.md), [정책 문서 작성 규칙](../../../docs/policies/documentation.md). 사용자의 최신 StatusBar 영향·필수 시험 근거·배포조건 재분석 및 조정 요청에 근거한 개발 담당의 판단이다. 사용자가 이 결정의 완성 문안이나 최종 파일 게시를 승인했다는 뜻은 아니다. 회사·조직의 배포 승인도 아니다.

대체·대체됨 관계: [ADR-0021](ADR-0021-R13-focused-wording-evaluation.md)의 native 전역 상태 전항목 PASS 조건 중 아래 StatusBar 실패만 부분 대체한다. 나머지 제작·소스·native·설치·복구·보안·해시 조건은 유지한다. [ADR-0020](ADR-0020-R12-wording-release.md)의 R12 한정 시험 생략 예외를 재사용하지 않는다. R11·R12의 실제 실패·미실행 및 전체 인수 미완료 판정을 바꾸지 않는다.

## 맥락

RC13 제품 변경은 첫 목록 확인 요약의 기존 **첫 번째 목록 바꾸기** 안내 한 줄과 릴리스·설치 버전이다. 실제 제작 입력의 동결 커밋은 `9ebaf3d661e1602e7bc6e60be4b9a0c0fe079160`, 후보 XLAM SHA-256은 `484419befa0cd763635b1f9592cff43bd13e657e19d5a693d76a78fa071ed14e`다. 격리 BuildOnly, 저장한 VBA 7개 모듈·RibbonX 대조와 현재 집중 13개 검사를 완료했다.

첫 native 시도는 실제 StatusBar FAIL을 포함한 부분 native FAIL과 미완료로 종료했다. 별도로 기존 R12의 UI 분리를 Workbooks 열거로 처리한 준비 결함을 확인했다. 메뉴 상태 간섭의 원인은 확정하지 않는다. 제품의 새 요약·Replace 전체 흐름 완료 결과가 아니다. 이 결과와 첫 시도의 Pos 값 복구 PASS를 각각 보존한다. 준비 도구에서 기존 R12를 정확한 이름의 Item으로 확인하고 해당 세션의 UI만 분리한 뒤 같은 후보로 두 번째 흐름을 실행했다. 기존 R12 설치·등록은 제거하거나 업그레이드하지 않았다.

두 번째 native 실행은 2026-10-03 13:35:21~13:55:43 UTC에 실제 UI 한 흐름으로 완료했다. 합성 원본 `Alpha/Beta/Beta`를 담고 한 Beta를 Gamma로 의도적으로 수정했으며 원본은 저장하지 않았다. 첫 확인 파일과 교체 전 새 확인 파일에는 Beta가 계속 남았다. 실제 기존 **첫 번째 목록 바꾸기** 명령을 UI에서 실행한 뒤 세 번째 확인 파일에 Gamma와 서로 다른 값 3개·추가 개수 0개가 반영됐다. 요약의 A14/B14 안내 전체가 실제 두 줄로 보였으며 14항목을 유지했다. 이전 확인 파일은 변하지 않았다.

전후 자료형을 포함한 전역 상태 8개 중 StatusBar만 Boolean False에서 String `FALSE`로 바뀌었다. native 원시 판정은 FAIL이며 flowComplete=true와 구분한다. 원본·이전 결과·나머지 전역·보안·기존 설치와 소유 정리 조건은 통과했다. cleanupErrors는 없고 소유 Excel이 자연 종료했으며 남은 Excel은 없다. 후보 해시는 변하지 않았다. 기존 제품·Setup 파일 10개의 해시, OPEN·제품 Trusted Location·보안·비교 설정은 기준과 일치한다. 정상 시작에서 바뀐 Options의 Pos 값은 원래 값임을 확인하는 방어 후 그 값만 복원해 최종 기준 일치를 확인했다. 제작의 두 임시 AccessVBOM 변경도 각각 값 부재 → DWORD 1 → 값 부재로 정확히 원복했다.

## 영향과 원인 판단

[Microsoft의 Application.StatusBar 문서](https://learn.microsoft.com/en-us/office/vba/api/excel.application.statusbar)는 False를 Excel이 상태표시줄을 제어하는 상태로 설명하며 False를 설정해 기본 표시를 복원하도록 안내한다. String `FALSE`가 남는 현상은 자료형 차이와 함께 이 제어권 복원이 되지 않는 표시 복원 결함이다. 프로세스 안에서 Excel의 평소 상태 표시가 가려질 수 있다.

이번 합성 흐름에서 새 안내·스냅샷·명시적 Replace와 원본·이전 결과 보존은 정상이다. 현재 증거상 복구 불가능한 상태나 데이터 기능의 중단을 뜻하지 않는다. 이를 모든 업무 자료의 무손실 보장으로 확대하지 않는다. 표시 결함의 영향은 평가판에서 제한을 공개하고 수용할 수 있는 범위로 판단하지만, 정상 복원 요구를 충족하거나 안정판 검증을 완료한 것으로 표시하지 않는다.

정확한 원인은 미확정이다. 현재 제품 소스는 이미 Boolean 분기에서 literal `Application.StatusBar = False`를 사용한다. R11의 새 세션 재현과 별도로 빈 COM 대조에서도 `FALSE` 문자열이 관찰된 적이 있다. 이 관찰은 제품·Excel·자동화 경계 또는 다른 추가 기능의 영향을 모두 배제한 원인 증명이 아니다. 수정 가능성은 있지만 검증되지 않은 한 줄 변경으로 해결된다고 주장하지 않는다. 원인 확인과 제품 수정은 이번 선택된 문구 후보의 완료 증거로 대신하지 않는다.

## 결정

`focused-wording-evaluation`의 서명 없는 평가 prerelease에 한해 위 정확한 StatusBar 실패를 명시적 opt-in으로 수용한다. 실제 시험을 삭제하거나 PASS로 바꾸지 않는다. native 전체 판정과 개별 StatusBar FAIL, 흐름 완료·다른 조건 PASS를 따로 보존한다. 허용 근거는 `USER_REQUESTED_ANALYSIS_AND_RELEASE_CONDITION_ADJUSTMENT`이며 `authorizationRecorded=true`는 그 요청과 개발 판단의 기록을 뜻한다. 최종 게시 승인이나 회사 승인을 뜻하지 않는다.

수용 기록은 `evaluationOnly=true`와 이 결정 파일의 실제 SHA-256인 `decisionSha256`을 후보 해시·실제 native 기록에 묶는다. 적용은 RC13과 위 후보에 한정하며 다른 자료형·값 변화, 다른 전역 실패, 원인 미확정 오류 전반을 포괄적으로 허용하지 않는다. 결정·후보·소스가 바뀌면 기존 수용을 자동 승계하지 않는다.

다음은 계속 필수다.

- 동결 소스·ASCII/UTF-8·버전·저장한 VBA 7개 모듈·RibbonX·후보 SHA의 일치와 현재 집중 13개 실제 결과.
- 실제 요약·스냅샷·명시적 Replace 한 흐름, 원본·이전 결과 보존, StatusBar를 제외한 자료형 포함 전역 상태 보존.
- 보안과 임시 AccessVBOM 정확한 원복, 기존 설치·등록·파일·설정 및 기존 Excel 보존, 소유 결과 정리·Excel 자연 종료와 cleanupErrors 없음.
- T11의 동일 후보 실제 엔진 설치·대표 비교·결과·제거와 초기 상태 복원. 현재 T11은 NOT_RUN이며 별도 일반 사용자 Windows·데스크톱 Excel 시험 환경 확보가 필요하다.
- 패키지·자산·소스·증거·버전·해시 대응, 문서 strict·생성 링크·공개 범위 확인. 원시 로그·레지스트리·개인 경로·화면·업무 자료는 공개하지 않는다.

`fullAcceptancePassed=false`, `stablePublishAllowed=false`, 평가 prerelease 한정과 서명·조직 환경 미확인을 유지한다. R11 취소 완료 안내 FAIL·StatusBar FAIL, 과거 부분 집계 82 PASS / 기존 기대값 1 FAIL / 스냅샷 누락 2 ERROR, R12 시험 NOT_RUN과 모든 초기 시도 실패를 그대로 보존한다.

## T11 순서와 배포 경계

T11은 설치·대표 비교·결과·제거의 최소 실제 엔진 흐름이다. 최종 EXE 시험을 마쳤다고 해석하지 않는다. 현재 설치 엔진은 자신의 폴더에 정확한 XLAM·Setup.ps1·Uninstall.cmd·README.md가 있으면 Install.cmd로 설치할 수 있다. 따라서 동결한 입력의 비공개 시험 payload 준비 → T11 → 최종 패키지 제작·검토 순서로 확인할 수 있으며 논리적 순환이 아니다.

package 전에 T11 증거를 요구하면서 최종 EXE를 package 단계에서 처음 만드는 순서로 최종 EXE 설치 검증까지 주장하면 순환이 생긴다. 비공개 엔진 payload의 검증과 최종 EXE 제작·구성 검증을 구분한다. 최종 EXE의 실제 설치·제거는 `newWrapperActualInstallation=NOT_RUN`으로 남긴다. 이를 완료해야 한다는 후속 요구가 생기면 비공개 후보 EXE 제작과 공개 게이트를 분리해 같은 EXE의 실제 시험·해시 고정 후 게시 판단을 해야 한다.

현재 계정에는 R12 설치·등록이 있다. 고정 제품 경로의 엔진을 이 계정에 설치하면 기존 R12 업그레이드가 될 수 있으므로 이 흐름을 실행하지 않는다. R12를 보존할 수 있는 별도 일반 사용자 Windows·Excel 환경에서 같은 후보와 동결 설치 입력을 확인한다. T11 미실행을 StatusBar 예외로 수용하거나 PASS로 바꾸지 않는다. 비공개 시험 payload 제작은 공개 설치 자산 게시가 아니다.

## 검토한 대안

- 모든 전역 PASS까지 평가판도 보류: 초기 ADR-0021의 엄격한 경로다. 기존 표시 실패가 그대로인 문구 후보의 평가 출하까지 막는 대신 전체 복원 기준을 유지한다.
- StatusBar 실패만 명시적으로 수용: 이번 채택안이다. 실제 실패와 안정판 금지를 유지하며 새 문구·Replace·보존·설치의 필요한 증거를 요구한다.
- R12 시험 생략 예외 재사용 또는 T11 생략: 새 후보의 실제 증거와 기존 다음 후보 설치 조건을 없애므로 채택하지 않는다.
- 원인 미확정 상태의 즉석 수정: 선택된 제품 범위가 늘어나고 새 후보·시험 근거가 필요하므로 이번 평가 수용과 섞지 않는다.

## 실패와 복구·안내

다른 전역·원본·이전 결과·보안·기존 설치·사용자 설정·소유 정리·자연 종료 실패나 후보·소스·증거 불일치는 포장·공개를 중단한다. 알 수 없는 문서나 사용자 Excel을 닫거나 강제 종료하지 않는다. 회사 정책·영구 매크로 보안·신뢰 저장소 변경을 요구하지 않는다. native에서 후보의 매크로 포함은 사람이 선택했으며 영구 보안 설정 변경·자동 우회로 확대하지 않는다.

공개 안내에는 상태표시줄에 `FALSE`가 남거나 Excel의 평소 상태가 가려질 수 있다는 영향과 미해결 상태를 적는다. 필요한 통합문서를 저장한 뒤 Excel을 정상 종료하고 다시 열어 상태를 확인하도록 안내한다. 강제 종료를 요구하지 않으며 이 절차가 원인 해결이나 재발 방지를 보장한다고 표시하지 않는다.

## 검증·현재 출하 판단

두 번째 native의 기능 흐름·다른 보존·정리 결과를 실제 기록과 대조하고, StatusBar FAIL만 이 결정의 opt-in과 해시로 수용한다. 수용 거절·다른 실패·다른 후보·조작된 PASS·결정 해시 불일치를 포장 도구에서 거절해야 한다. 이는 제품 기능의 추가 시험이나 전체 suite 통과가 아니다.

T11·최종 EXE·ZIP·패키징·병합·태그·GitHub Release와 공개 다운로드 갱신은 아직 NOT_RUN이다. #13은 소스 준비 Draft PR이며 기존 R12 공개 자산·다운로드를 유지한다. T11과 나머지 필수 근거를 확보한 뒤 평가 prerelease의 구체적 자산·범위·출하 판단을 다시 한다. 이번 문서 갱신 후 strict·링크 확인은 별도 실행 대기다.
