# Excel 명단 비교 · 2026-09-17 오류 재실험

> **후속 작업:** 이 기록을 마친 뒤 사용자가 임시 VBA 개발 접근과 자율적인 후속 검증·릴리즈 진행을 명시적으로 허용했다. 승인 후 RC9 작업은 [새 제작·재검증 기록](RC9_APPROVED_RETEST_20260917.md)을 따른다. 아래 본문은 허용 전 RC7 재실험과 당시 종료 상태의 기록으로 보존한다.

날짜: 2026-09-17 · 상태: **재실험·원복 완료, 새 RC9 릴리즈 보류.**

공개 RC7의 고정 XLAM을 다시 설치해 실제 Excel에서 입력 12가지를 끝까지 비교했다. 각 목록 20,000개인 48자 고유값은 결과 40,000행을 만들었지만, 각 50,000개 비교는 약 30초 처리 지연 보호로 중단됐다. 설치 실행기의 별도 모듈 검색 경로 오류는 재현·수정했다. 이 결과를 새 RC9 비교 엔진의 실행 결과로 사용하지 않는다.

새 RC9 XLAM은 아직 없다. 현재 `AccessVBOM`이 비활성화돼 있으며 `Build-ExcelCandidate.ps1`의 `ApprovedTemporaryVbaAccess` 사용에 필요한 별도 허용 답변을 기다린다. 이는 회사 정책 결정이 확인됐다는 뜻이 아니며 해당 값이나 조직 정책을 변경하지 않았다. RC7의 비교는 즉시 Esc 입력에서 취소되지 않았고 100ms·500ms 누름에서는 취소를 관찰했다. **첫 목록 바꾸기는 500ms 입력에도 취소되지 않고 100,000개로 교체됐다.** 수정 실행기의 추가 설치 1회 실패는 뒤의 반복 성공으로 지우지 않았다. 최종 Python·문서 검사는 통과했고 재실험 후 미설치 상태로 원복했다. 기존 [RC8 실패](RC8_COMPLETION_REPORT.md)와 [RC9 이전 기록](RC9_STABILITY_REPORT.md)은 보존한다.

## 실제 용량 시험

각 목록은 별도 시트의 단일 세로 선택이다. `고유값`은 A/B 간 겹치는 값이 없는 경우이며, `절반 일치`는 값의 절반이 같은 경우다. 여러 Selection 영역이 겹치는 시험이라는 뜻은 아니다. 표의 시간은 `Application.Run` 호출의 경과 시간으로 경고 응답·포커스와 관찰 대기가 포함될 수 있다. 소스 준비·결과 확인은 제외했지만 범위 검사·읽기·비교·출력을 각각 분해한 값은 아니다.

`DuplicateMaxChars1221`은 `x` 4,096자 셀 1,220개와 `y` 2,880자 셀 한 개이며 A/B 내용은 같다. 원문 합계는 정확히 5,000,000자다. 결과 1행은 중복값 행이며 마지막 단일 값은 일치한다. 이 시험은 5,000,000개의 고유 문자값을 결과로 출력했다는 뜻이 아니다.

10,000개의 97.670초에는 화면 관찰·포커스·경고 응답 대기가 들어 있으므로 처리 속도로 해석하거나 20,000개의 13.086초와 처리량을 비교하지 않는다. 50,000개의 124.294초에도 대화상자 대기가 포함되며 제품의 약 30초 체크포인트 제한이 124초라는 뜻이 아니다. 20,000개에서 관찰한 시간도 이 PC·해당 자료의 단일 실행값이며 최대 지연 보장이 아니다.

증거는 저장소 루트의 `artifacts/excel-retest-20260917/rc7-capacity-{small,core,text,large}/capacity.json`에 있다. 실행기는 `tests/windows-capacity-matrix.ps1`이다. 앞선 세 그룹은 각각 PASS이고 large 그룹은 50,000개 실패를 포함해 FAIL이다. 그룹의 10,000개·20,000개 완료 사실과 그룹 전체 실패를 함께 기록한다.

이후 소유권 확인을 보강한 실행기로 `Unique100`을 다시 실행해 PASS했다(`rc7-capacity-guard-check/capacity.json`). 성공한 용량 실행은 총 13회이며 서로 다른 입력 조건은 여전히 12가지다. 재실행을 새로운 입력 범위 확인으로 세지 않는다.

## 보존·복구와 실패 해석

완료한 12가지 모두 독립 기대 요약과 결과 행 수를 확인했고 결과 `HasFormula=False`였다. 원본 저장 파일의 SHA-256, 원본 Saved 상태, ScreenUpdating·EnableEvents·Interactive·EnableCancelKey·Calculation·DisplayAlerts·AutomationSecurity를 확인했다. 각 세션에서 표본으로 읽은 `Workbooks.Count` 최대값은 2였다. 연속 관찰한 최대값이 아니며 추가 기능까지 포함한 모든 열린 파일 수를 뜻하지 않는다.

50,000개 실패에서도 원본 SHA-256·Saved·위 설정과 XLAM 해시는 유지됐다. `new-result` 단언은 실패로 남겼다. 출력 완료 요구의 실패를 지연 보호 동작의 성공으로 바꾸지 않는다. 이번 용량 JSON은 실패 뒤 첫 목록의 모든 값을 다시 비교하는 단언과 이전 편집 결과 보존 시험을 포함하지 않으므로 그 요구 전체를 이번 결과만으로 PASS라고 하지 않는다.

네 그룹 모두 `cleanupErrors=[]`, `ownedExcelExited=true`이고 감독 실행기 마지막 관찰에도 새 Excel 프로세스가 남지 않았다. 이는 각 용량 시험의 정상 종료 확인이며, 제품 설치·보안 설정까지 시험 시작 상태로 되돌리는 최종 원복 확인과 별도다.

## 실제 Esc 입력과 복구

위와 같은 RC7 XLAM에서 첫 목록 42개와 서로 다른 48자 값 100,000셀을 사용했다. Win32 도구는 소유 프로세스의 정확한 제품 경고를 관찰·수락한 뒤 대화상자가 사라지고 시험 실행기의 처리 신호가 있는 상태에서 `SendInput`으로 Esc를 전달했다. 물리 키보드 시험이 아니며 운영체제가 입력 이벤트를 받아들였다는 결과만으로 Excel 수신을 확정하지 않는다. 전경 창 변경 가능성과 정확한 Excel 수신 시각은 측정하지 못했다.

| ID·로컬 증거 폴더 | 입력 조건 | 실제 응답 | 보존·종료 판정 |
|---|---|---|---|
| RETEST-E01 / `esc-compare-tap` | Esc down/up 즉시 전송, 2/2 이벤트 수락. 입력 호출 22:24:51 UTC | 22:25:20 UTC에 약 30초 지연 보호와 오류 `-2147219401`. **Esc 취소 실패** | 첫 목록 42개로 후속 비교 정상. 보존 단언 통과. helper 전체 FAIL은 정상 Quit 뒤 3초 이내 종료 관찰 실패도 포함. 후속 같은 소유 PID 관찰에서 종료 확인 |

시각은 원시 기록의 UTC이며 실험일의 한국 시각과 혼동하지 않는다. E02·E03은 해당 비교 입력에서 취소와 복구를 관찰한 결과다. E04에서 500ms 바꾸기가 실패했으므로 오래 누르면 모든 작업을 안전하게 취소할 수 있다는 안내를 하지 않는다. helper의 `nativeEscVerified=false`와 `NOT_CLASSIFIED_BY_HELPER`는 자동으로 성공을 판정하지 않는 설계다. 제품 결과 JSON과 별도의 입력·대화상자 관찰 JSONL에 나타난 실제 응답을 함께 읽었다. E04에서도 Excel의 실제 키 수신은 직접 측정하지 못했다.

E01~E03의 보존 단언에는 원본 저장 파일 SHA-256·Saved, 이전 결과 T1 시험 표식·Saved, Excel 설정 7개와 후속 42개 일치 결과·수식 없음이 포함된다. 각 20개 PASS에는 준비 확인과 반복 확인이 섞여 있으므로 독립적인 안전 요구 20개 통과라고 집계하지 않는다. E04의 13개 단언에는 42개 기준을 실행 전에 담은 준비 확인이 포함되지만 실행 후 42개 보존은 포함되지 않는다. 모든 셀의 메모리 값·서식·필터를 전수 비교한 시험은 아니다. E01의 원래 FAIL·종료 지연 기록은 후속 종료 관찰로 덮어쓰지 않는다.

시험 보조 코드에는 E01·E02 이후 소유권 확인과 실행 소스 SHA-256 기록을 보강했고 E03·E04에서 사용했다. 앞선 실행을 보강된 코드로 실행했다고 소급하지 않는다. RC9 소스에는 이미 별도 체크포인트·확정 복구 변경이 있지만 새 바이너리를 실행하지 않았으므로 이번 RC7 결과로 그 변경의 효과를 판정하지 않는다.

## 자원과 시험 운용

감독 실행기의 기본 시작 기준은 CPU 65% 이하·메모리 사용 80% 이하·여유 메모리 2GB 이상이다. 시작이 차단된 기록은 세 번이다. 한 번은 동일 사용자 세션의 시험 잠금 때문이고, 두 번은 CPU 표본 74.7%와 78.8%가 기준을 넘어서였다. CPU 때문에 세 번 차단된 것으로 집계하지 않는다.

이후 용량 기능 시험은 실행별 `MaxBaselineCpu=90`으로 시작 기준을 임시 지정했다. 메모리 기준은 유지했고 영구 제품 설정이나 PC 자원 제한을 변경하지 않았다. 시험은 한 번에 하나씩, 자식 래퍼 BelowNormal 우선순위로 실행했다. 이 임시 시험 조건에서 얻은 결과를 저부하 성능 보장으로 발표하지 않는다.

|---|---:|---:|---:|---:|
| retest-rc7-small-2 | 17.6 | 17 | 100 / 69.0 | 4.93 |
| retest-rc7-core | 8.6 | 26 | 86.2 / 68.0 | 5.09 |
| retest-rc7-text | 6.5 | 21 | 100 / 68.0 | 5.09 |
| retest-rc7-large | 9.4 | 128 | 99.2 / 68.2 | 5.05 |

CPU·메모리는 PC 전체의 주기 관찰값이다. Excel 단독 점유율, 연속 최대값이나 입력 지연의 원인으로 단정하지 않는다. 일부 CPU 표본은 값이 없으므로 최대값 계산에서 제외했다. 자원 원시 기록은 `artifacts/excel-bounded/retest-rc7-*/telemetry.private.jsonl`이며 래퍼 결과는 같은 폴더의 `result.private.json`에 있다.

[ADR-0013](ADR-0013-Windows-module-path.md)에 따라 `Install.cmd`, `Uninstall.cmd`, `Test_Excel.cmd`의 `setlocal` 안에서 모듈 경로를 Windows 기본으로 정한다. 부모 프로세스·사용자·컴퓨터 환경변수, 회사 정책, 영구 실행 정책과 설치 거래는 변경하지 않는다. 변경은 새로 포장할 실행기에만 적용한다. 이미 공개한 ZIP·EXE와 이번 실행한 RC7 XLAM은 변경하지 않았다.

직접 설치의 코드 6 뒤에는 미설치 상태로 롤백했다. 데스크톱 경로 시험은 이전 검증에서 사용한 일반 사용자 실행 방식을 재사용했으며 관리자 권한으로 올리지 않았다. 임시 작업 실행·제거 기록은 `artifacts/excel-retest-20260917/desktop-install-rc7/`에 보관한다. 사용자 경로·레지스트리·원시 진단은 공개 사이트와 배포 자산에 복사하지 않는다.

첫 반복 설치 기록은 `launcher-lifecycle.private.json`, 추가 진단은 `install-diagnostic.private.json`, 작업별 출력 수집 재실행은 `lifecycle-captured/results.private.json`에 있다. 첫 실행의 출력 누락은 실패뿐 아니라 성공한 작업에서도 관찰돼 누락 자체를 I07의 원인으로 판정하지 않았다. 재실행 10개 작업이 모두 성공해도 I07의 코드 1 원인은 미확정이며 RC9 릴리즈 게이트를 열지 않는다.

## 최종 원복

`restoration-audit.private.json`과 `restoration-residue.private.json`은 PASS다. 시작 전과 같은 제품 미설치 상태이며 제품·설치 관리 폴더, 제품 앱 등록(검사한 네 레지스트리 보기), `SLC-retest*` 시험 작업과 Excel 프로세스가 남지 않았다. 추가 레지스트리 복구를 수행할 필요가 없었다.

Office·PowerShell 관련 HKCU/HKLM 14개 분기의 값 이름·종류·실제 값 집합과 실행 정책은 시작 전과 같았다. 기준 자료에 빈 키 구조는 포함되지 않았으므로 전체 레지스트리 구조가 완전히 같다는 보장은 아니다. 임시 VBA 접근·매크로 보안·영구 실행 정책은 변경하지 않았다.

로컬 시험 자료와 제거 실행기의 임시 복사본은 보존했다. 업무 문서를 사용하지 않았으며 이 자료·계정 경로·원시 로그를 공개 사이트나 배포 파일에 넣지 않는다.

## 명세 반영과 남은 검증

[제품 명세](../../../docs/tools/excel-list-compare/specification.md)에 입력 안전 상한과 실제 완료 관찰 범위를 분리했다. 현재 100,000셀 상한은 읽기 허용 여부의 방어값이며 그 크기까지 완료한다는 약속이 아니다. 이번 관찰로 48자 고유값 각 20,000개·결과 40,000행의 완료는 기록할 수 있지만 모든 20,000셀 조합·PC·필터 조각의 정상 동작을 선언하지 않는다. 긴 값과 원문 총길이의 별도 PASS를 20,000셀과 결합하지 않는다.
