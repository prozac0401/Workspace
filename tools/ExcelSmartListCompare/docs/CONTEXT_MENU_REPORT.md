# RC7 · 메뉴를 열 때 목록 상태를 다시 구성

후속 수정과 현재 파일의 검증 결과는 [RC8 검증 기록](RC8_COMPLETION_REPORT.md)을 따른다. 아래는 해당 버전 당시의 기록이다.

도구 ID: ExcelSmartListCompare · 설치기 버전: 0.2.0-rc.7 · 날짜: 2026-09-15

상태: 서명되지 않은 후보. 아래는 잠금 상태에서 수행한 최초 자동 검증 기록이다. **잠금 해제 후 실제 우클릭 8종과 두 파일 열기 경로는 통과했고, Esc 취소는 2회 실패했다.** 최신 화면·설치·원복 결과는 [실제 화면 검증](UNLOCKED_UI_REPORT.md)을 따른다. 전체 인수 완료로 표시하지 않는다.

적용 기준: [추가 도구 개발 기준](../../../docs/policies/tools.md), [문서 작성 규칙](../../../docs/policies/documentation.md), [ADR-0008](ADR-0008-Context-menu-content.md), [인수 요구 U07~U13](ACCEPTANCE_TESTS.md)

## 사용자 재보고와 변경 이유

RC6 설치 후에도 서로 다른 Excel 창의 컨텍스트 메뉴가 다르다는 보고가 있었다. 사용자는 두 파일을 각각 열거나 첫 파일에서 두 번째 파일을 여는 방식 모두에서 같다고 확인했다. 파일 열기 방식이나 별도 프로세스를 원인으로 단정하지 않는다.

[RC6 검사](WINDOW_STATE_REPORT.md)는 CommandBar 속성과 창 활성화 이벤트를 확인했다. 실제 우클릭으로 Excel이 표시한 메뉴는 확인하지 못했으므로, 그 통과 결과만으로 사용자 화면 문제가 해결됐다고 볼 수 없다. 이번 읽기 전용 확인 시에는 기존 Excel 프로세스와 제품 설치가 없었다. 합성 파일과 RC6로 준비한 창을 확인하던 중 잠금 화면을 발견해 네이티브 UI 조작을 중단했고 시험 설치를 원복했다. 사용자 화면의 재현·원인은 아직 확정되지 않았다.

## 구현

XLAM의 RibbonX `dynamicMenu`가 열릴 때마다 현재 첫 번째 목록을 읽어 메뉴 내용을 구성한다. `invalidateContentOnDrop="true"`를 사용해 창 이벤트에 의존하던 기존 컨텍스트 메뉴 갱신을 대체했다. 일반 셀·행·열, 표와 페이지 레이아웃의 총 8개 메뉴 위치를 연결했다. [Microsoft 규격과 근거](SOURCES.md)를 따른다.

| 첫 번째 목록 상태 | 메뉴 내용 |
|---|---|
| 없음 | 첫 번째 목록 담기 / 사용 안내 |
| 있음 | 두 번째 목록 담아 비교 / 첫 번째 목록: n개 항목 / 첫 번째 목록 비우기 / 첫 번째 목록 바꾸기 / 사용 안내 |

담기와 비교의 실행 진입점도 분리했다. 비교 명령에 첫 번째 목록이 없으면 담기로 바꾸어 실행하지 않고 안내한다. 추가 기능 탭의 기존 도구 모음은 유지한다. 사용 안내에는 설치 파일을 식별할 수 있도록 `0.2.0-rc.7`을 표시한다.

메뉴 내용 생성은 셀값·선택·활성 창·이벤트 설정을 변경하지 않는다. 비교 엔진은 그대로이며 스냅샷은 같은 Excel 프로세스의 메모리에 둔다. 별도 프로세스 사이의 공유는 이번 변경 범위가 아니다. 이 경계를 사용자 재보고의 원인 설명으로 사용하지 않는다.

## 검증 대상과 제작

- 환경: Windows 11 23H2, 데스크톱 Excel x64 `16.0.20326.20144`, Windows PowerShell 5.1, 일반 사용자.
- 새 XLAM SHA-256: `5da5ff891232dde733d60ee6151cbfb26e251d6b75a51cb6a3f224effde4c18b`
- 저장된 VBA 5개 구성 요소를 소스와 대조했다. VBE 식별자 대소문자와 모듈 속성만 보정하고 문자열은 그대로 대조한다. 주 모듈은 1,004행, 최장 ASCII 행은 321자다.
- RibbonX XML도 원본과 패키지를 대조하고, Office 관계·콘텐츠 형식·8개 메뉴 ID를 확인한다. 배포 검사기에 이 검사를 추가했다.

기존 승인에 따라 제작 동안만 VBA 프로젝트 접근을 허용했다. 정상 Excel에서 가져오기·저장·제품 메타데이터와 RibbonX 기록을 수행한 뒤 권한을 원복했다. 새 파일을 제품 경로에 설치하고 정상 시작에서 실행했다. 기본 `Build_Release.cmd`의 단독 재열기 경로 전체가 성공했다고 기록하지 않는다.

164개 단언은 메뉴 XML 생성 함수를 직접 호출해 반환 내용을 검사하고, 해당 작업의 공개 VBA 명령을 실행한다. 두 파일, 비우기·바꾸기, 새 파일·새 창, 담은 원본 닫기, 비교 후 초기화와 원본 파일 해시 보존을 포함한다. Office `getContent` 호출 시점이나 실제 `onAction` 클릭을 시험한 것으로 기록하지 않는다. `onLoad` 통과도 모든 메뉴 위치의 실제 표시 증거가 아니다.

선택 14개는 가로↔세로, 사각형, 한 셀, 여러 영역·겹침, 전체 행·열, 숨김 행·열, AutoFilter·표 제목·합계, 수동 계산과 같은 범위 스냅샷이다. 결과 수식 없음·설정 복원·사용자가 편집한 이전 결과 보존을 확인했다.

## 최초 원복과 후속 확인

임시 VBA 접근은 원래 미설정 상태로 돌렸다. 시험 설치는 시작 전처럼 미설치이며, 창 위치를 포함한 Office·PowerShell 관련 14개 설정 그룹을 복원했다. 남은 Excel 프로세스는 0개이고 임시 예약 작업도 제거했다. 원시 계정·설치 로그·합성 파일은 로컬 artifacts에 보관하며 배포에는 식별자 없는 요약만 넣는다.

후속 [잠금 해제 시험](UNLOCKED_UI_REPORT.md)에서 두 파일을 각각 여는 경우와 첫 파일에서 두 번째 파일을 여는 경우를 모두 실행했다. 실제 우클릭의 담기·비교·개수·비우기·바꾸기·완료 후 초기화와 8개 메뉴 위치를 확인했고, 이 환경에서는 창별 메뉴 불일치가 재현되지 않았다. 이벤트를 끈 조건에서는 동적 메뉴가 최신 4개를 표시했으나 기존 도구 모음은 42개를 표시했다.

최초에는 경고·일치·오류·도움말 대화상자와 실제 Esc 입력을 실행하지 못했다. 후속 화면 시험에서 대화상자는 확인했지만 UI 도구로 입력한 Esc는 두 번 모두 취소되지 않았다. 이전 캡처·이전 버전 결과로 통과 처리하지 않는다. 모든 문서를 닫은 채 Excel만 남긴 뒤 다시 여는 경로, 다른 Office 버전·x86·조직 정책·전자 서명·타사 추가 기능 전반의 공존은 이번 인수 범위에 포함하지 않는다. 업데이트 중단과 복구의 범위는 [RC6 설치 검증의 제한](UPGRADE_REPORT.md)을 유지한다.

RC7 배포본의 `Validation.json`은 `contextMenuContent`와 `nativeContextMenu`를 별도 항목으로 기록한다. 전자가 통과해도 후자는 미실행일 수 있다. `BUILD_INFO.json`, `SOURCE_COMMIT.txt`, `SHA256SUMS.txt`에 정확한 파일·소스 정보를 포함하며 prerelease로 배포한다.
