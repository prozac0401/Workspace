# RC10 전체 흐름 검증 기록

상태: 부분 검증 · 기존 RC9 파일 5개 물리 복원·등록 보존 확인 · 상태표시줄 형식 복원 실패 및 후속 설치·UI 미검증 유지 · 2026-09-20 · 로컬 시험 후보 0.2.0-rc.10

이번 기록은 [사용성 개선 검증](USABILITY_RC10_REPORT.md)에 이어 설치부터 정상 시작, 비교, 재시작, 재설치, 제거와 기존 설치 복원까지 확인한다. 전체 인수 또는 회사 도입 승인을 뜻하지 않는다.

## 고정한 시험 파일

- EXE SHA-256: `d9b270253a979d09e4dbc517956e98014a79a550553b221064398cd1d18299a7`
- XLAM SHA-256: `2386375cbe0aec6e62fdfa2129cfbc18d358451666504be8bab2fab3c33f719b`
- 기존 RC9 XLAM SHA-256: `61574c0f0acc68fb7b49507fa95c7201768515f4c5edfd563e3caf3915c19efc`

시험 파일은 `artifacts/excel-rc10-package-20260919/package-01`의 로컬 후보다. 실행 중 새로 빌드해 해시를 바꾸지 않는다. 시험 전 자동화 환경에서 CMD 방식 RC9의 파일 5개와 설치 기록을 읽었지만 자동 로드 OPEN 등록과 제품 신뢰 위치, 단일 EXE 앱 등록과 제거 관리 디렉터리는 관측되지 않았다. 이 관측을 기준으로 파일·등록 상태를 백업했다. 후속 일반 Windows 진단에서는 원래 RC9 기록과 일치하는 OPEN·신뢰 위치 등록이 확인됐다. 따라서 초기 자동화 환경의 등록 부재를 일반 Windows의 원래 등록 상태로 확대하지 않는다.

후속 `package-02`는 설치기의 시스템 `chcp.com` 경로 수정을 반영해 별도로 생성했다. EXE SHA-256은 `91d0223bf1a786b08fc981bb2779de67407688be504ea76167b84fddcb4a6725`이며 XLAM은 위와 같은 바이트다. 초기 합성 시험은 동일 XLAM에 한해 참조하며 새 EXE 설치 성공으로 옮겨 적지 않는다. 두 패키지 모두 서명되지 않은 로컬 시험 후보이며 전체 인수 승인은 없다.

## 증거와 제한

비공개 원시 기록은 `artifacts/excel-rc10-e2e-20260919`에 보관한다. 계정 식별자·레지스트리 값·로컬 설치 로그는 공개 사이트와 공유 패키지에 넣지 않는다. 시험 도구가 만든 합성 통합문서만 사용하며 사용자 문서를 저장하거나 종료하지 않는다.

초기 화면 도구 시간 초과와 시스템 자원 부족이 있었다. 이후 사용자가 계속 진행하도록 요청했고, Excel 프로세스가 모두 종료된 상태와 자원 회복을 확인했다. 앞선 도구 실패를 제품 실패나 시험 통과로 집계하지 않는다.

첫 백업 시도는 PowerShell 매개변수 기본값에서 실행기 경로를 계산하다가 중단했다. 두 번째는 설치 기록의 신뢰 위치가 실제로도 존재한다고 가정한 사전 검사에서 중단했다. 두 시도 모두 제품을 변경하기 전이며, 실제 등록 부재를 읽기 전용으로 확인해 반영한 Plan03에서 백업을 완료했다.

기존 상태 정상 시작 시험 두 번은 자동 로드·메뉴 부재를 확인했지만 정상 Quit 후 프로세스가 남았다. 첫 시험은 빈 통합문서 상태에서 재차 Quit하고 20초를 기다려도 남았다. COM 참조 정리와 추가 종료 대기를 보완한 두 번째 시험도 종료 성공으로 판정하지 않았다. 두 시험 프로세스는 PID·시작 시각·현재 COM 연결 대상·통합문서 0개·보호된 보기 0개·표시 창 부재를 확인한 뒤 해당 PID만 정리했다. 사용자 프로세스는 정리 대상으로 삼지 않았다.

후속 실행기는 자식의 Quit 요청과 부모의 실제 프로세스 종료 확인을 분리한다. 정상 종료가 실패한 경우 선택적인 빈 시험 프로세스 정리로 나머지 검사를 진행할 수 있지만, 그 실행은 `PARTIAL`이며 정상 종료 실패가 유지된다. 미확인 문서·다른 Excel 프로세스·소유권 불일치가 있으면 정리와 다음 설치를 중단한다.

단일 EXE 시도 두 번은 `PREPARE_START` 다음 접근 거부 코드 5로 실패했고 `PREPARE_ENTERED`·`ENGINE_START`에 도달하지 못했다. 두 번째 시도는 제품 상태가 변경되지 않았음을 확인했다. 같은 실행기를 대상으로 한 별도 회귀도 9개 시험 중 11개 하위 실패·1개 오류로 끝났다. 관련 시간대의 AppLocker·Code Integrity·Defender 기록에는 원인을 입증하는 사건이 없었다. 보안 정책 때문이라고 단정하거나 정책을 완화하지 않았다.

설치 로그에서 별도로 확인한 `chcp` 검색 실패는 시스템 `chcp.com`의 명시 경로를 사용하도록 수정했다. 이 변경은 PATH·PATHEXT 의존성을 없애며 PowerShell 접근 거부의 해결을 뜻하지 않는다. 실행기 시험도 시스템 PowerShell을 명시적으로 선택하고, 호스트 시작 전 실패의 오류 코드와 환경 변수 존재 여부를 비공개 기록에 남기도록 보완했다. 관련 합성·정적 회귀 14개를 통과했다. 변경한 EXE는 기존 패키지를 덮어쓰지 않고 별도 후보로 다시 패키징한다.

문서에 명시된 `Setup.ps1 -Action Install -ConfirmProduct` 직접 경로는 성공했다. EXE 성공으로 대신 판정하지 않고 Engine 결과로 분리했다. 첫 Engine 기능 시험은 숨겨진 XLAM을 일반 Workbooks 열거에서 찾으려던 검사 결함으로 중단했다. 이 결과만으로 제품 자동 로드 실패라고 단정하지 않는다. 관찰 전용 파일명 조회로 검사기를 수정한 뒤 후속 시험을 진행한다. Engine01 이후 기존 파일 5개·메타데이터·제품 등록과 다른 추가 기능·정책 보존을 확인했다.

[Microsoft의 Workbooks 설명](https://learn.microsoft.com/en-us/office/vba/api/excel.application.workbooks)에 따르면 열린 추가 기능은 컬렉션 열거에 포함되지 않지만 파일명으로 조회할 수 있다. 검사기는 `Workbooks.Item(filename)`만 사용하도록 수정했으며, 추가 기능을 직접 열거나 UI 연결 함수를 호출하지 않는다. `Count=0`이지만 이름 조회가 숨겨진 XLAM을 반환하는 모의 회귀, 없는 이름 처리, RPC 거절과 부재의 구분, 컬렉션 참조 해제를 모두 통과했다. 이 모의 회귀는 실제 자동 로드나 Excel 정상 종료의 통과 증거를 대신하지 않는다.

Engine02·03은 설치된 XLAM의 자동 로드와 버전을 확인했지만, 숨겨진 Excel에서 도구 모음을 찾지 못해 기능 시험이 중단됐다. 두 실행 모두 기존 파일과 등록을 정확히 복원했다. 이후 Engine04에서 같은 후보를 실제 표시된 Excel로 시험한 결과, 도구 모음 8개와 우클릭 메뉴가 존재하고 동작했다. 숨겨진 상태의 관찰 실패를 실제 메뉴 누락으로 판정하거나 근거 없이 제품 UI 코드를 바꾸지 않는다.

실제 화면 시험은 원본 A·B 각각 7개 항목, 고유값 6개, 중복 1개, 공백·오류 각 1개인 합성 파일을 사용했다. 미리보기 3시트, 규칙 적용 후 동일 비교 4시트(일치 7, 남는 항목 0/0), 첫 목록을 유지한 두 번째 비교 4시트(7 대 3, 일치 1, 남는 항목 6/2)를 확인했다. 두 번째 결과를 닫고 앞선 결과를 다시 확인해 수치 보존도 확인했다. 목록 교체 후 출처와 3개 항목 표시, 비우기 후 원본 셀 보존을 확인했다.

별도 합성 파일의 50,000개 × 96자 선택은 경고에서 아니요를 선택하면 작업을 시작하지 않고 첫 목록을 유지했다. 계속 진행한 시험에서는 읽기 진행을 관찰한 뒤 실제 Esc와 표시된 취소 버튼을 입력했으나 최종 안내는 시간 초과 `-2147219401`이었다. 불완전 결과는 남지 않았고 첫 목록 3개는 유지됐다. 이는 오류 후 보존의 증거이며 사용자 취소 성공 또는 50,000개 처리 성능 보장이 아니다.

UiFixture가 만든 파일 두 개의 해시는 시험 전후 일치했고 소유 Excel은 정상 종료됐다. 이후 별도 Excel 프로세스와 오피스 자동화 도구가 시작되어 해당 세션을 보존하고 후속 설치를 중단했다. Engine04 복원 시점에는 Excel 프로세스가 없어 기존 파일 5개·메타데이터·제품 등록과 보호 대상 설정을 정확히 복원했다. 후속 NoAddin 시작에서는 제품 로드 부재를 확인했지만 이름으로 도구 모음을 조회하는 검사에서 `0x80070057`이 발생했다. 정상 Quit 뒤 남은 프로세스는 PID·시작 시각·연결 대상과 문서/보호된 보기 0개·표시 창 부재를 확인한 뒤 해당 시험 PID만 정리했다. 이 정리는 정상 종료 통과로 취급하지 않는다. 후속 점검에서 Excel 프로세스 0개를 확인했다.

Engine05는 모든 모드에서 소유 통합문서를 표시한 상태로 관찰했다. 자동 로드와 메뉴 검사는 통과했으나, `SLC_Capture` 호출 전 `System.Boolean false`였던 StatusBar가 호출 후 `System.String "FALSE"`로 변경되어 설정 복원 검사가 실패했다. 화면에서만 관찰한 미리보기 문제보다 앞선 담기 단계에서 자료형 불일치를 재현한 것이다. 나머지 애플리케이션 설정은 같았고 합성 원본 해시는 유지됐으며 해당 기능 시험 Excel은 정상 종료됐다. 이후 기존 설치를 정확히 복원했다. 이 실행에서 재시작·재설치·제거·새 설치는 실행하지 않았다.

메뉴 부재 관찰은 `0x80070057`을 무조건 부재로 취급하지 않도록 보완했다. 전체 열거에서 대상 이름이 없고, 열거에 실제 존재하는 이름의 명명 조회가 성공하며, 열거에 없는 GUID 이름의 조회가 같은 오류로 끝나고 대조 전후 목록이 같을 때만 부재를 인정한다. 모의 대조 10개와 통합 조회 2개를 통과했다. 실제 기존 환경에서도 제품 자동 로드 부재와 이 대조에 의한 메뉴 부재를 확인했다. 정상 Quit 이후 빈 소유 프로세스가 남는 결과는 별도로 실패로 유지했다.
