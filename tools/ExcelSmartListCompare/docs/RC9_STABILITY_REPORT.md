# RC9 · 처리 부하와 설치 안정성 재검증

날짜: 2026-09-17 · 상태: **소스 보완·실행 가능한 회귀 검사 완료, 필수 실기 대기. 출시 보류.** 새 XLAM의 실제 Excel 검사와 네이티브 Esc·대화형 설치 검증을 완료하지 않았다. 완성된 출시 버전으로 분류하지 않는다. [기계 판독용 검증 요약](../evidence/rc9/validation.json)

## 대상과 변경

현재 작업 대상은 `Workspace` 저장소의 RC9 소스다. 이전 RC8의 [실패 기록](RC8_COMPLETION_REPORT.md)과 고정 바이너리 해시는 그대로 보존한다. 이후 한국어 문구 교정도 이번 소스에 포함한다.

- [처리 부하·취소 결정](ADR-0011-Bounded-processing-and-cancellation.md): 블록별 좌표 조회, 단일 영역의 불필요한 중복 사전 제거, 문자열 전체 재연결 제거, 비교·출력·확정 직전 취소 확인과 이전 목록 보존.
- [설치 실행기 결정](ADR-0012-System-PowerShell-launcher.md): 시스템 Windows PowerShell을 명시하고 준비·본체·거래 실패 단계를 로컬에 기록한다. 접근 거부를 자동 재시도로 숨기지 않는다.
- 시험 자체도 한 번에 하나씩 실행하고 자원을 기록한다. 선택 시나리오는 문서를 계속 쌓지 않고 이전 결과 하나만 다음 검사까지 보존하도록 바꿨다.

이 변경으로 RC8의 실제 Esc 실패 원인이 확정되거나 해결됐다고 주장하지 않는다. 성능 개선량도 새 바이너리에서 측정하기 전에는 수치로 표시하지 않는다.

실행기 검사 세부사항과 이전 접근 거부 분석은 [설치 진단 기록](INSTALLER_RC9_DIAGNOSTICS.md)을 따른다. 소스 변경 이후의 통과 기록만 해당 소스에 적용한다. 최종 76개에는 실행기 8개, 감독 실행기 5개, 빌드 경로 보호 3개와 배포 거부 3개가 포함되므로 별도 합산하지 않는다. 앞선 70개·66.897초 기록도 보존한다.

## 부하 기록과 시험 실패 이력

짧은 Excel 사전 검사의 8개 자원 표본은 CPU 최고 70.3%, 메모리 최고 61.8%, 여유 메모리 최소 6.07GB였다. 이는 PC 전체의 해당 표본이며 Excel 단독 사용량이나 이전 RC8 시험 당시의 부하를 뜻하지 않는다. 입력 지연과 자원 점유의 인과관계는 아직 확인하지 못했다.

감독 실행기는 기본적으로 시작 전 CPU 65%·메모리 사용 80%·여유 2GB 기준으로 시작 여부를 판단한다. 실행 중 자원은 기록하며 자동으로 사용률을 제한하는 기능은 아니다. 기존 Excel이 있으면 시작하지 않고, 시간 초과에도 사용자 Excel을 강제 종료하지 않는다.

첫 사전 검사의 감독 기록에는 Quit 직후 Excel이 잠시 남은 것으로 관찰됐다. 이어 확인했을 때 같은 PID는 종료돼 있었다. 감독 실행기는 이 종료 지연을 구분하도록 최대 3초 대기와 즉시·최종 관찰을 각각 기록하게 보완했다. 영향을 받는 성공·시간 초과 검사를 다시 통과했다.

신뢰 위치 격리 검사의 첫 실행은 기존 `Release` 폴더의 XLAM이 없어 준비 단계에서 중단됐다. 기능 실패로 바꾸어 설명하지 않는다. 이 검사는 Excel을 실행하지 않는 파일·레지스트리 함수 시험이므로 자체 합성 패키지를 만들도록 고쳤고 새 증거 폴더에서 23개를 통과했다. 이전 실패 기록은 삭제하지 않았다.

로컬 증거: `artifacts/excel-rc9-20260917/`, `artifacts/excel-bounded/rc9-*`. 계정·경로·레지스트리·원시 진단은 공개 사이트에 포함하지 않는다.

## 이어서 통과해야 할 항목

1. 허용된 개발 환경에서 새 XLAM을 만들고 VBA·RibbonX와 소스를 대조한다. 임시 개발 권한을 허용받았다면 Excel 종료 후 원래 값·형식·존재 여부를 확인한다.
2. 같은 파일로 실제 통합·메뉴·선택 검사를 실행한다. 마지막 부분 청크, 결과 출력 끝, 첫 목록 교체 중 오류의 복구를 확인한다. 주입한 취소를 실제 Esc 성공으로 집계하지 않는다.
3. 작은 목록부터 큰 목록까지 한 번에 하나씩 시험하고 CPU·메모리·처리 시간과 취소 결과를 기록한다. 시험 문서는 최대 3개로 유지한다.
4. 실제 화면 조작이 가능한 세션에서 처리 중 Esc를 반복 확인한다. 도구의 입력 호출, Excel의 응답과 완료 결과를 구분한다. 최종 해시가 바뀌면 이전 키 시험을 재사용하지 않는다.
5. 같은 최종 EXE로 일반 사용자 최초 설치 반복·재설치·업데이트·제거·복구·대화형 취소를 확인한다. 설치 실패가 다시 발생하면 추가된 단계 진단으로 위치를 좁힌다.
6. 모든 필수 인수가 통과한 뒤에만 버전별 입력 해시와 출시 문서를 확정한다. 코드 서명·회사 인수 승인과 다른 Office 환경은 별도 범위로 표시한다.

재개용 `tests/Build-ExcelCandidate.ps1`은 새 로컬 출력 폴더에 후보를 만든다. `ApprovedTemporaryVbaAccess` 옵션은 별도 허용이 있을 때만 사용한다. 강제 제한시간 종료에서는 `finally`가 실행되지 않으므로, 사용한 감독자가 먼저 기록한 `access-before.private.json`으로 해당 값만 복원해야 한다. 이번에는 그 옵션이나 실제 빌드 경로를 실행하지 않았고 경로 보호·문법 검사만 통과했다.

## 원복

시험 시작 시 제품은 미설치였고 Excel은 실행 중이지 않았다. 이번 독립 회귀는 합성 시험 폴더와 별도 HKCU 분기만 사용했다. 제품 설치·신뢰 위치 등록·영구 실행 정책 변경은 하지 않았다. 개발용 VBA 접근 값도 바꾸지 않았다. 최종 대조에서 14개 레지스트리 그룹의 값·형식과 제품 파일 상태가 같았고 Excel 프로세스는 없었다. 비교는 키·값 이름의 대소문자와 열거 순서만 정리하고 중복 수와 실제 값·형식을 보존했다. 코드·문서의 공개 게시와 릴리즈 업로드는 하지 않았다.
