# ADR-0013 · 보이는 칸 붙여넣기의 명시적 COM 참조 수명

상태: 수정 설계 채택 · 2026-09-26 후속 0.1.1 설치본의 실제 사용·종료 및 제거·재설치 확인. 패키지·게시 결과는 별도 배포 기록

날짜: 2026-09-24 · 검증 상태 갱신: 2026-09-26

결정 담당: 도구 개발·검증 담당

관련 요구사항·정책: [ADR-0010](0010-visible-cells-paste-com.md), [원본 작업지시](../tools/visible-cells-paste/original-specification.md), [도구 개발 기준](../policies/tools.md)

대체·대체됨 관계: ADR-0010의 독립 COM 구조는 유지하며 COM 참조 수명과 종료 검증을 보완함.

## 맥락

0.1.0 게시 후 합성 파일에서 실제 메뉴를 사용하고 Excel을 닫는 검사에서 종료 실패가 3회 발생했다. 붙여넣기만 수행한 경우도 포함한다. 기본 Excel 복사·붙여넣기·실행 취소 후 닫는 제한된 대조 시나리오는 정상 종료했다. 당시 덤프에는 CLR 종료의 RCW 정리·SafeReleasePreemp와 잘못된 COM 해제 호출 대상이 관찰됐으나 책임 객체는 특정하지 못했다.

2026-09-26 초기 0.1.1 설치본은 실제 업그레이드와 두 UI 사용 후 종료를 통과했다. 이후 상태바 정확 복원을 보완한 최종 후보는 자동 로드·붙여넣기 성공 뒤 08:32:09 UTC에 BEX64/c0000409 종료 충돌이 재현됐다. 새 사건의 덤프가 없어 이전 CLR 스택이 반복됐거나 최근 변경이 원인이라고 단정하지 않는다.

추가 경계 검토에서 ComEventsHelper가 사용하지 않는 이벤트 인자까지 VARIANT에서 관리 객체로 바꾸는 경로, 연결 Application 참조의 반환 책임, IDTExtensibility2 custom ABI 및 실행 중 재진입한 연결 종료를 보완 대상으로 정했다. 미사용 이벤트 RCW가 충돌을 일으켰다는 결론은 아니다. 원시 덤프·개인 경로·실행 식별자는 저장소·배포물·공개 사이트에 포함하지 않는다.

## 결정

Excel 객체는 Excel 호출 스레드에서 사용하며 실제로 획득한 참조와 반환 책임을 추적한다.

- Range·Collection·열거자·스냅샷 읽기 참조는 해당 작업 범위가 소유하고 예외 경로에서도 반환한다.
- PreparedPaste는 보유한 Workbook·Worksheet·Selection의 소유자다. 엔진으로 소유권을 넘긴 뒤 추가 기능이 다시 정리하지 않는다. 동일 작업 재진입 거절은 바깥 실행의 참조를 폐기하지 않는다.
- Ribbon callback과 연결 추가 기능 인자는 각 획득 경로에서 한 번 반환한다. OnConnection의 Application 획득 한 번은 추가 기능이 소유하고 연결 정리 마지막에 반환한다. 엔진·Undo 관찰자는 이를 빌리고 반환하지 않는다. 동일 RCW의 여러 획득도 획득 횟수대로 관리한다.
- IDTExtensibility2의 custom은 설치된 PIA에 맞춘 [In] 참조 배열로 선언한다. 연결 실패·재연결 실패에도 전달받은 새 인자의 반환 책임을 유지한다.
- UndoEpoch는 전용 IDispatch sink로 기존 14개 이벤트 DISPID만 관찰한다. DISPPARAMS·VARIANT를 읽거나 관리 객체로 변환하지 않고 Cancel 인자도 수정하지 않는다. 자기 connection point와 Advise cookie만 소유하며 Unadvise 실패에도 획득한 참조를 반환한다. 연결 실패는 Available=false로 처리한다.
- 명령·확인창·진행·상태 타이머 callback 중 연결 종료가 재진입하면 새 작업을 막고 마지막 활성 callback이 끝난 뒤 pending·엔진·타이머·Application을 정리한다. 연결이 끝난 뒤 늦은 이벤트·안내는 실행하지 않는다.
- 중복 Dispose는 이미 반환한 참조를 다시 반환하지 않는다. 공유 객체의 임의 FinalReleaseComObject·강제 GC를 수명 계약의 대용으로 사용하지 않는다.

## 검토한 대안

| 대안 | 판정 |
|---|---|
| 관리 필드 null과 자연 GC만 유지 | 종료 RCW 정리 실패가 있어 충분한 수명 근거가 아님 |
| 임의 강제 GC·모든 RCW 최종 해제 | 공유 참조와 소유권을 구분하지 못해 다른 작업을 손상할 수 있음 |
| ComEventsHelper의 공유 callback 인자를 임의 반환 | 같은 관리 인자를 받는 다른 callback과 소유권을 분리하기 어려움 |
| 이벤트 인자를 해석하지 않는 전용 sink | 사용하지 않는 RCW 변환을 피하고 자기 연결만 관리. native ABI와 실제 Excel 이벤트·종료 검증이 필요 |
| 명시적 범위·소유권 이전·활성 callback 후 정리 | 채택한 방향. 자동 검사 통과와 실제 설치본 종료 성공은 별도 게이트 |

## 영향과 이행

복사·선택·우클릭 흐름, 값·타입·서식 정책과 최근 한 번 Undo 안전 조건은 유지한다. 상태바는 저장값의 타입·값을 정확히 복원하며 현재 Excel에서 Boolean false 할당이 문자열 FALSE로 남으면 확인된 reset 뒤 다시 검증한다. 실제 문자열은 그대로 보존한다. 이 정확 복원 문제와 종료 충돌의 인과관계는 확정하지 않는다.

0.1.0 릴리스는 초안으로 전환하고 최신 표시를 해제했으며 태그는 유지한다. 0.1.1은 후속 설치본의 두 실제 사용 후 종료를 확인했으며 최종 검증 문서·패키지·CI·게시 절차를 마친 뒤 공개한다. 0.1.0의 게시 전 69 PASS/7 NOT RUN 표는 당시 스냅샷으로 보존한다. 공개 사용 안내에는 시험 진행 상태를 추가하지 않는다.

## 실패와 복구

COM 정리가 실행됐다는 이유로 셀 복구를 성공 처리하지 않는다. 쓰기 전 검증·전체 백업·부분 실패 복구·전역 상태 복원·복구 미완료 차단은 유지한다. 전역 상태 복원 자체 실패는 state-restore-failed로 후속 쓰기를 막고, 완료 후 안내 실패는 이미 완료된 셀 작업과 분리한다.

Excel이 남아 있으면 설치·제거를 중단한다. 초기 0.1.1 업그레이드와 후속 제거·메뉴 부재·재설치는 이 가드를 유지한 채 통과했다. 이전 후보 종료 충돌 뒤 접근 거부되는 잔여 프로세스가 생겨 새 후보 설치가 차단됐다. 사용자가 잔여 프로세스를 정리한 뒤 Excel 0개를 확인하고 후속 DLL을 설치했다. 접근 거부를 안전한 종료로 추정하거나 설치 가드를 우회하지 않았다.

## 검증

초기 build02의 189개 자동 검사와 두 실제 UI 종료 PASS를 보존한다. 후속 상태바 수정 후보는 206개 자동 검사 및 실제 R17·제거·재설치를 통과했으나 사용 후 종료는 FAIL이었다. 해당 후보의 기능 시험 59개 본문 PASS와 wrapper 상태 복원 FAIL도 분리한다.

새 수명 소스의 full-build-03은 9종 284개를 통과했다. 여기에는 x64/x86 각각 36개의 COM·native 이벤트 검사, 연결 수명 46개, 안내/진입 26개가 포함된다. QI 정체성·IDispatch vtable·14개 이벤트·Cancel 불변·빈 결과·늦은 callback을 native 호출로 검사했다. connection point의 실패·cookie 정리는 가짜 객체 주입이며 실제 Excel 연결 검증이 아니다. x86 프로세스 시험도 32비트 Excel 실행 통과를 뜻하지 않는다.

실제 60개 기능·복구는 모두 통과했고 scope exit0·cleanup0이다. 기존 파일 SHA·선택·워크북 개수·Protected View와 5개 전역 속성의 실제 타입·값이 정확히 복원됐다. Boolean false와 실제 문자열 FALSE를 각 쓰기·거절·복구 경로에서 구분해 보존하는 추가 시험도 통과했다. 새 생산 DLL의 R17은 4종·8회 거절과 클립보드 불변을 확인했다. 외부 시험 엔진과 기존 설치 추가 기능이 함께 있는 시험 호스트이므로 새 설치본의 자동 로드·종료 결과와 구분한다. 이후 생산 DLL `7080305a…`를 실제 설치한 두 정상 시작의 자동 메뉴로 붙여넣기 및 별도 붙여넣기·즉시 Undo를 수행했다. UI 저장 안 함 뒤 각각 540초·381초의 독립 관찰에서 해당 프로세스가 없고 새 Excel 오류 이벤트·WER가 없었다. 이는 이 설치본의 두 합성 시나리오 결과이며 이전 충돌 원인 객체나 모든 종료 조건을 증명하지 않는다. 동일 DLL의 비승격 제거·제거 후 메뉴 부재·재설치도 확인했다. 재설치 후 붙여넣고 숨김을 풀어 숨긴 원래값 보존을 직접 확인했다. 재설치 세션을 저장하지 않고 닫은 뒤 123초의 독립 관찰에서 프로세스 부재·새 오류/WER0·파일 SHA 불변도 확인했다. 문서 반영 패키지·CI·실제 공개와 다운로드는 외부 배포 기록으로 확인한다. 제품 소스는 PR #7로 main에 반영했다. 식별값과 근거는 [시험 보고서](../../tools/VisibleCellsPaste/docs/test-report.md)를 따른다.

## 공식 구현 근거와 한계

.NET Framework의 [ComEventsSink 구현](https://github.com/microsoft/referencesource/blob/main/mscorlib/system/runtime/interopservices/ComEventsSink.cs)은 이벤트 VARIANT를 관리 객체로 바꾸고 연결 cookie를 관리한다. 이를 근거로 미사용 인자 변환을 제거할 경계를 정했으나 제품 충돌 원인을 증명하지는 않는다. [ReleaseComObject 문서](https://learn.microsoft.com/en-us/dotnet/api/system.runtime.interopservices.marshal.releasecomobject?view=netframework-4.8.1)의 공유 참조·잘못된 해제 위험에 따라 획득 근거 없는 일괄 반환을 하지 않는다.
