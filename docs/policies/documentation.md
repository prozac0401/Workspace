# 정책 문서 작성 규칙

정책: 정책 문서 작성 규칙 · 상태: 제안 · 버전: 0.20 · 책임: 저장소 관리 담당 · 적용: 모든 현재·향후 도구와 운영 정책

## 원본과 문서 종류

편집 원본은 docs/의 Markdown이며 GitHub Pages는 빌드 결과입니다. 최초 명세는 요구의 근거로 보존합니다. 구현 상태는 명세 대응표와 검증 기록에서 표시합니다.

사용자 요청에 따라 ProbPacker의 Office Automation Tools 0.3.1 다운로드·사용 안내 한 페이지를 공개 범위에 추가합니다. 원본 저장소는 비공개이므로 [ADR-0034](../design/0034-office-automation-public-guide.md)에 따라 같은 단일 EXE와 두 ZIP만 Workspace의 `office-automation-tools-v0.3.1` Release 자산으로 공개하고 안내에서 연결합니다. 개발 저장소의 공개 범위는 바꾸지 않습니다. 공개 소개는 MS Office Excel·PowerPoint(PPT)·Word용 도구와 Python 없이 실행하는 방법으로 설명합니다. 공개 본문·제목·검색에는 ProbPacker 저장소의 이름과 존재·접근권한 설명을 넣지 않습니다. 제품명은 Office Automation Tools로 표기합니다. 서명·실행 검증의 실제 결과와 남은 확인 항목은 배포 기록에 보존합니다. 실행 기록·사용자 설정·업무 자료·로컬 검증 원문은 공개 사이트에 포함하지 않습니다.

DownloadVersionManager의 사용·설치 안내도 공개 허용 범위에 포함합니다. 확장이 필요한 0.1.0은 미완료 평가 버전으로 보존합니다. 실제 설치·실행·관련 실패 복구를 확인한 정상 0.2.1 MSI는 사용자의 명시 승인에 따라 Release의 버전별 자산으로 안내합니다. 공개 안내는 설치·사용·실제 지원 제한을 설명하고 확인하지 못한 환경과 시험 결과는 배포 기록에 보존합니다. 조직 도입·상용 승인으로 표시하지 않습니다. 실제 Release·자산 확인 후에만 게시 완료를 선언하고 Pages는 설치 파일을 복사하지 않고 해당 Release 자산에 연결합니다. 0.2.0의 공개본과 초기 실패 시험본이 달랐다는 검증 한계와 과거 기록은 보존합니다. 내부 실기 기록·개인 경로·SID·installer 진단·실패 주입 MSI는 공개 사이트와 Release 자산에서 제외합니다.

GitHub Pages의 공개 범위에는 가짜 자료로 설명하는 교육 업무 활용 안내 한 페이지도 포함합니다. 실제 명단·메일·업무 경로와 첨부 검토 원문은 공개 사이트로 복사하지 않습니다. [ADR-0029](../design/0029-education-public-guide.md)에 따라 기존 도구의 기능 안에서만 예시를 작성하고, 회사 설정과 실제 효과는 제안·미확인으로 구분합니다.

교육 업무 안내에는 가짜 자료로 만든 가상 화면을 브라우저에서 촬영한 그림 일곱 개를 넣을 수 있습니다. 그림과 설명에는 **‘설명용 예시 화면’**이라고 표시합니다. 실제 프로그램을 실행해 찍은 사진이나 기능 성공을 확인한 증거로 설명하지 않습니다. [ADR-0030](../design/0030-education-example-screens.md)에 따라 새로 공개할 파일은 `assets/education-examples/`의 `compare.png`, `paste.png`, `export.png`, `collect.png`, `image.png`, `bookmark.png`, `state.png`뿐입니다. 화면을 만드는 원본 `docs/illustrations/education-examples/screens.html`, 추가 JavaScript·HTML·글꼴·연습 파일은 사이트에 복사하지 않습니다. 실제 명단·개인 경로·로컬 진단 정보도 넣지 않습니다. 공개 문서 20개와 이전 주소 이동 문서 2개는 유지하며 새 메뉴는 만들지 않습니다.

GitHub Pages의 공개 범위는 업무 운영 정책과 FolderState·Excel 명단 비교·업무 책갈피(WorkBookmark)·선택범위 내보내기·File List to Excel·보이는 칸 붙여넣기·그림 복사·저장의 다운로드·사용·설치·오류 해결 안내입니다. 설치 파일은 각 도구를 배포하는 GitHub 저장소의 Release 버전별 자산으로 제공하며 사이트 출력에 복사하지 않습니다. 공개 안내는 원칙적으로 버전별 자산에 연결하고, 보이는 칸 붙여넣기는 아래 예외에 따라 배포 목록으로 안내합니다. 개발 정책, 명세, ADR, 문서 양식, 빌드·배포·검증 기록은 저장소에 보존하고 사이트에서 제외합니다. 공개 문서에서 제외 문서로 연결하지 않으며, 사용자에게 필요한 지원 제한은 설치 안내에 직접 요약합니다. 이 구분은 저장소 자체의 접근권한을 변경하지 않습니다.

독자에게는 [지금 할 일 찾기](../quick-reference.md) → [업무 하나로 시작하기](../getting-started.md) → 자료 정리 안내 순으로 안내하고, 조직별 인수인계·재개·효과 측정 개선안은 선택 적용으로 표시합니다. 요약 안내에서 새 의무를 만들지 않으며 상세 정책의 해당 기준으로 연결합니다. 기록 부담을 늘리는 변경에는 실제 반복 불편과 중복 기록을 줄일 방법을 함께 적습니다.

FolderState의 공개 안내는 설치·사용·문제 해결을 한 페이지와 메뉴 한 항목으로 제공합니다. 기존 설치·문제 해결 주소에는 통합 페이지의 해당 부분으로 이동하는 문서만 생성하며 메뉴·검색·사이트맵에 별도 안내로 싣지 않습니다.

새 파일은 기본적으로 사이트에 포함하지 않습니다. 공개할 문서·자산은 mkdocs.yml의 exclude_docs 허용 항목에 명시하고 scripts/check-site.py의 공개 목록도 함께 갱신합니다. 새 공개 문서는 탐색 메뉴에도 추가합니다. 기존 문서에 설명 그림만 넣을 때는 새 메뉴를 만들지 않습니다. 세부 결정은 [ADR-0004](../design/0004-public-handbook.md), Excel 안내·다운로드 범위를 확장한 [ADR-0006](../design/0006-public-tool-downloads.md), 업무 책갈피 안내를 추가한 [ADR-0008](../design/0008-bookmark-public-guide.md), 두 Excel 도구 안내를 추가한 [ADR-0011](../design/0011-excel-tools-public-guides.md), 보이는 칸 붙여넣기의 사용 안내를 추가한 [ADR-0012](../design/0012-visible-cells-paste-public-guide.md), 그림 복사·저장의 공개 안내를 추가한 [ADR-0025](../design/0025-image-public-guide.md)를 따릅니다.

2026-10-06 사용자 요청과 [ADR-0035](../design/0035-public-tool-wording.md)에 따라 GitHub Pages는 기능·다운로드·설치·사용 방법을 중심으로 씁니다. 정식 배포·평가용·시험용 등 배포 단계 표현과 내부 시험 수치·미확인 환경 경고는 공개 안내와 검색 항목에서 제외합니다. 실제 버전·파일명·고정 다운로드 연결, 데이터 보존에 필요한 제한과 알려진 문제의 해결 방법은 유지합니다. 실제 화면의 버튼 이름은 사용자가 찾을 수 있도록 그대로 적습니다. 배포 채널·검증 판정과 미실행 항목은 사이트에서 제외한 배포 기록에 보존하며 문구 정리를 조직 도입·상용 승인으로 해석하지 않습니다. 소스 교정과 설치 파일 제작·검증·게시를 구분하고, 이전 설치 파일에 아직 반영하지 않은 변경을 적용됐다고 설명하지 않습니다. 회사별 설정의 제안·미결정 표시는 유지합니다.

| 종류 | 대답할 질문 | 위치·표기 예 |
|---|---|---|
| 정책 | 어떤 기준을 따르는가 | policies/ · 기본 구조와 원본 |
| 도구 명세 | 무엇을 하고 어디까지 하는가 | tools/도구명/ · REQ-도구-001 |
| ADR | 왜 이 설계를 선택했는가 | design/ · ADR-0001 |
| 실행 안내 | 어떻게 사용·복구하는가 | 도구별 사용·설치·오류 안내 |
| 검증 기록 | 어떤 환경에서 무엇을 확인했는가 | delivery/ |
| 양식 | 다음 문서를 어떻게 시작하는가 | forms/ |

보이는 칸 붙여넣기의 공개 안내는 2026-09-24 사용자 요청에 따라 다운로드·설치·사용·지원 범위·복구·제거를 중심으로 구성합니다. 이 페이지와 검색 항목에는 평가·시험 상태·시험 결과를 넣지 않으며 내부 근거는 저장소에 보존합니다. 이 표현 원칙은 2026-10-06부터 위 규칙에 따라 전체 공개 안내에 적용합니다. [ADR-0014](../design/0014-visible-cells-paste-download-list.md)에 따라 공개 다운로드 진입점은 Workspace Releases 목록으로 연결하며, 제품명과 Assets의 설치 파일 이름으로 선택하는 순서를 안내합니다. [ADR-0019](../design/0019-visible-cells-paste-single-installer.md)의 단일 EXE를 기본 설치 경로로, 기존 ZIP을 대안으로 안내합니다. 이 페이지에는 특정 버전과 직접 자산 URL을 고정하지 않습니다. 지원하지 않는 입력과 복구 제한, 코드 서명 없음과 보안 정책 적용은 공개 안내에 직접 설명합니다. 공개 범위 변경이 내부 판정이나 회사의 승인 여부를 바꾸지는 않습니다.

## 정책 필수 내용과 상태

정책은 내용을 알 수 있는 자연어 이름으로 표기합니다. 머리말에는 정책 이름을 쓰고, 본문·표·변경 이력에서 다른 정책을 참조할 때는 해당 정책 이름과 문서 링크를 사용합니다.

정책 이름, 상태, 버전, 책임 역할, 범위, 목적, 규칙, 예외, 검증, 근거, 변경 이력을 적습니다. 상태는 제안 → 검토 → 승인 → 대체/폐기입니다. 문서 작성만으로 회사 정책이 승인되었다고 표시하지 않습니다. 실제 승인자와 적용일은 결정 후 기록합니다.

## 변경 절차

1. 실제 불편이나 위험 사례와 변경할 문서의 이름·링크를 연결합니다.
2. 행동·데이터 계약·권한·배포 방식이 바뀌면 ADR을 작성합니다. 문구 수정마다 ADR을 늘리지는 않습니다.
3. 소스·정책·사용 안내·검증을 같은 변경에서 맞춥니다.
4. PR에 변경 전후 행동, 이유, 호환성, 검증과 미확정 항목을 적습니다.
5. 문서 strict 빌드와 관련 도구 검증 후 검토자가 승인합니다.
6. 변경 이력과 Pages 배포 결과를 확인합니다.

Git은 누가 무엇을 바꿨는지를, ADR은 왜 바꿨는지를 설명합니다. 승인된 ADR은 후속 ADR로 대체 관계를 남깁니다.

## 문서 품질

### 처음 읽는 사람도 행동할 수 있게 씁니다

사용 안내와 프로그램 문구는 사전 교육이나 특정 학력을 전제로 쓰지 않습니다. 아래 기준을 문장마다 확인합니다.

1. 제목과 첫 문장에 사용자가 할 일을 씁니다. 예: ‘최소 도입’ 대신 ‘업무 하나로 시작하기’.
2. 한 문장에는 한 가지 행동이나 설명을 담습니다. 여러 행동은 실제 순서대로 나눕니다.
3. 추상적인 원칙보다 상황과 예를 먼저 보여줍니다. 예: ‘업무 컨테이너’ 대신 ‘이번 업무의 자료를 모은 폴더’.
4. 공개 안내의 설명은 중등교육 수준의 비전공자가 이해할 수 있는 일상말로 씁니다. 전문용어는 넣지 않고 사용자가 할 일과 생기는 결과로 풀어 씁니다. 실제 제품명·버튼명·파일명·필요한 명령어는 찾아 사용할 수 있도록 그대로 적되, 쉬운 말로 목적을 설명합니다.
5. 버튼은 누른 뒤 생기는 일을 말합니다. 예: ‘상태 표시 지우기’. 오류는 무슨 일이 안 됐는지와 사용자가 다음에 할 일을 알려줍니다.
6. 같은 행동은 화면·메뉴·설치 안내에서 같은 말로 씁니다. FolderState 상태명은 ‘시작 전 / 진행 중 / 완료 / 확인 필요’입니다.
7. 필요한 안내와 선택 사항을 구분합니다. 문구를 쉽게 바꾸면서 새 의무를 추가하거나 기존 제한을 숨기지 않습니다.

검토할 때는 제목·문장·표의 칸·버튼·오류를 각각 분리해 읽습니다. `scripts/review-wording.py`는 현재 공개 안내와 프로그램의 문구를 출처별로 추출하고 이전 버전과 비교합니다. 기술 명세와 과거 검증 기록은 당시의 근거로 보존합니다.

실제 이해도는 처음 사용하는 사람이 설명 없이 업무 하나를 끝내는지 확인해야 합니다. 문구 검토나 자동 빌드만으로 모든 사람이 이해한다고 판정하지 않습니다.

제안·구현·자동검증·수동검증·미검증을 구분합니다. 실제 조직 설정을 만들어 넣지 않습니다. 정책과 구현이 다르면 차이·이유·영향·조치를 명세 대응표에 기록합니다. 예외도 담당과 적용 범위를 남깁니다.
