# ExcelPasswordSafe · 암호 작업 성능 개선 기록

기록 시작: 2026-11-17 · 버전: 3 · 상태: 성능 개선 구현·관련 검증 완료
관련: [사용자 원문](../tools/excel-password-safe/original-request.md), [명세](../tools/excel-password-safe/specification.md)의 REQ-EPS-024, [버전 2 검증](excel-password-safe-v2-20261117.md)

## 요청과 범위

사용자는 게시된 버전 2를 사용한 뒤 “암호화 복호화가 지나치게 오래걸립니다.”라고 피드백했다. 작업 단계를 측정해 실제 지연 원인을 좁히고 필요한 부분만 개선한다. 측정 전 개선 시간·배율을 추정하거나 특정 병목을 원인으로 단정하지 않는다.

기준은 [ExcelPasswordSafe 2 릴리스](https://github.com/prozac0401/Workspace/releases/tag/excel-password-safe-v2), 릴리스 ID `447717481`이다. 게시와 공개 다운로드 검증은 완료됐으며, 기준 MSI의 SHA-256은 `D25D849687F2D90F483E86ADC10F461DA64DCD775552ABF30BB080A491006C53`이다. 기준 소스는 `f784f95`이며 이전 검증의 PASS·NOT RUN은 당시 결과로 보존한다.

## 변경과 충분한 완료 근거

기준 계측에서는 작은 파일에서도 Excel 시작·종료 시간이 큰 부분을 차지했다. 폴더 배치가 소유한 Excel 인스턴스를 같은 배치의 파일 사이에서 유지하여 시작·종료 반복을 줄이는 변경을 구현했다. 파일별 백업·검증·원자 교체는 유지한다. 내용 비교용 배열의 XML 직렬화는 형식 구분을 보존한 스트림 해시로 바꿨다. 직접 OOXML 암호화 라이브러리로 암호 구현을 교체하지 않으며 Excel 저장·재열기 경로를 유지한다. 기능 회귀 통과와 전체 시간 개선 여부는 별도로 판단한다.

세션은 첫 처리 가능한 파일에서 시작한다. 고정한 Excel PID·시작 시각과 토큰·작업 순번·idle ACK, 열린 통합문서 0개를 확인한 뒤에만 파일별 교체를 허용한다. 다음 파일은 앞 커밋·정리 이후에 처리한다. 커밋 직전 UI 소유 프로세스·취소를 확인하고, 프로토콜·RPC·정리·종료가 불확실하면 후속 처리를 중지해 필요한 복구 자료와 루트 `NeedsInspection` 보고를 보존한다. 구체적 결정은 [ADR-0040의 성능 후속 결정](../design/0040-excel-password-safe-folder-batch.md), 실제 검증 범위는 아래 근거를 따른다.

같은 입력 복사본·작업·환경에서 단계별 시간과 전체 시간을 비교하고, 해당 변경에 직접 연결되는 내용·암호 검증과 원본 보존 회귀 결과를 확인한다. 변경하지 않은 화면·설치의 수동 시험이나 무관한 전체 시험을 반복하지 않는다.

원본 백업, 고정한 해시, 암호 설정·해제·변경의 재열기와 잘못된 암호 거절, 내용 비교, 원자 교체, 취소·중복 실행·안전한 재시도·중간 파일 정리 계약은 유지한다. 속도를 위해 이 검증을 생략하지 않는다. 암호나 업무 내용은 계측 자료에 기록하지 않으며 로컬 진단 원문은 공개 자산에 넣지 않는다.

## 기준 작업 시간

로컬 근거는 `artifacts/excel-password-safe/baseline-small-001/profile.json`이다. 기존 worker 복사본에 구간 계측만 더하고 합성 `.xlsx`의 암호 설정→해제를 각각 한 번 실행했다. 설정 전 원본은 6,184바이트이고, 이어 해제한 암호 파일은 16,896바이트였다. 두 실행 모두 `Success / ReplacedAndVerified`다. 이 표는 기준 실행 시간이며 개선 후 비교가 아니다. 단위는 밀리초다.

| 구간 | 암호 설정 | 암호 해제 |
|---|---:|---:|
| 전체 엔진 실행 | 18,727.72 | 14,593.12 |
| worker 실행 | 15,156.90 | 10,405.48 |
| Excel 시작 | 5,201.11 | 2,066.65 |
| 저장 전 내용 서명 | 532.09 | 416.13 |
| 저장 후 내용 서명 | 368.33 | 1,177.22 |
| Excel 종료·COM 해제 | 3,100.77 | 4,025.30 |

전체 엔진 시간은 worker와 제어·전달 시간을 포함하며 표의 행을 모두 합산하지 않는다. 설정과 해제는 입력 상태·실행 순서가 다르므로 두 열의 차이를 개선 효과로 읽지 않는다. 한 환경의 각 1회 기준 측정으로 모든 파일의 병목이나 고정 처리 시간을 단정하지 않는다.

## 내용 비교 코드의 별도 시험

`artifacts/excel-password-safe/signature-001/signature-results.json`의 순수 관리 배열 시험 34개가 PASS다. null·빈 문자열, 숫자·문자·불리언·오류, 수식 텍스트, Unicode, 배열 차원·하한·순서와 형식 차이를 구분하며 알 수 없는 형식은 거절하는 경로를 확인했다. Excel이나 통합문서 파일을 사용하지 않은 시험이다.

| 합성 배열 규모 | 기존 XML 직렬화 | 형식 구분 스트림 해시 |
|---|---:|---:|
| 100,000셀 | 901.973ms | 33.130ms |
| 400,000셀 | 3,783.352ms | 165.461ms |

새 helper의 첫 컴파일 시간은 별도로 660.876ms였다. 표의 계산 시간에 이 준비 비용이나 Excel 시작·저장·재열기·원본 교체 시간이 들어 있지 않다. 따라서 이 수치를 실제 암호 작업 전체의 개선 배율로 사용하지 않는다. 같은 순수 검증은 `signature-002/signature-results.json`에서도 34개 PASS이며, 위 시간은 최초 001 실행의 값으로 보존한다.

## 초기 전체 시간 비교 · 부하 조건 불일치

`baseline-batch-001`과 `optimized-batch-001`의 초기 전체 시간을 아래에 보존한다. 개선 후보 실행 때 순수 회귀 시험이 병렬로 실행되어 부하가 통제되지 않았다. **설정·변경은 후보가 더 오래 걸렸다.** 이 결과를 지우거나 부하만이 원인이라고 단정하지 않으며, 아래 숫자로 전체 작업의 개선을 선언하지 않는다. 단위는 밀리초다.

| 작업 | 파일 수 | 기존 방식 | 세션 재사용 후보 |
|---|---:|---:|---:|
| 암호 설정 | 2 | 28,619.32 | 42,688.57 |
| 암호 변경 | 2 | 32,898.37 | 48,319.38 |
| 암호 해제 | 2 | 36,375.29 | 24,655.16 |
| 잘못된 암호로 해제 3회 | 1 | 37,100.27 | 16,091.90 |

앞 세 행은 양쪽 모두 `Success`이며 마지막 행은 의도한 `Failed` 결과다. 기존 방식은 앞 세 행마다 Excel 2개, 실패 재시도에는 3개를 시작했고 후보는 각 행에서 1개를 사용했다. 인스턴스 감소 자체를 시간 개선의 증거로 대체하지 않는다.

## 단독 구간 계측 · 비교 판정 제외

추가 `worker-profile-run-001/profile-summary.json`은 다른 순수 시험과 겹치지 않게 실행한 계측 결과다. 설정은 21,719.907ms, 해제는 22,451.038ms였고 둘 다 `Success`였다. 설정의 최초 helper 컴파일은 405.351ms, Excel 시작은 1,323.603ms, 두 번째 작업의 시작부터 결과 기록까지는 약 4.54초, 마지막 Excel 종료는 2,841.609ms였다.

이 실행은 구간 계측을 더한 후보 실행이며 앞 기준과의 통제된 전후 비교가 아니다. 이 값만으로 전체 처리 속도나 처리량 개선을 주장하지 않는다.

## 동일 입력의 비계측 비교

측정 환경은 Windows 11 23H2 x64(build 22631.6199), Windows PowerShell 5.1.22621.6133, Excel 실행 파일 버전 16.0.20527.20196이다. 기존 core 기록과 실행 중 바이너리·OS 메타데이터를 읽기만 해 대조했으며 별도 Excel을 시작하거나 연결하지 않았다. 근거는 `docs-performance-001/environment.json`이다.

`performance-large1-001/performance-results.json`은 10,000행×40열, 400,000셀의 합성 파일 하나를 순차 비교했다. 설정 입력은 1,309,029바이트, 해제 입력은 1,394,688바이트이며 각 작업의 기존·후보 입력 SHA-256이 같다. 제어 프로세스 시작부터 종료까지 측정하고 자료 생성·시험 하네스 검증 시간은 제외했다. 실행 순서는 기존 설정→기존 해제→후보 설정→후보 해제이며, 작업·runtime별 관측은 각각 1회다. 반복 평균이나 캐시 영향을 분리한 분포 측정은 아니다.

| 큰 파일 1개 | 기존 방식 | 최종 안전 검사 포함 후보 | 관측된 시간 감소 |
|---|---:|---:|---:|
| 암호 설정 | 21,396.28ms | 18,891.77ms | 11.7% |
| 암호 해제 | 19,980.71ms | 18,776.89ms | 6.0% |

네 실행 모두 `Success`였고 원본과 같은 백업·커밋 결과 해시·중간 작업/암호 전달 파일 정리·Excel 종료를 확인했다. 측정된 후보 runtime 4개의 해시는 당시 최종 소스와 일치했다. 파일 하나는 여전히 Excel 시작·종료와 저장·재열기 비용이 필요하며 이 결과는 제한된 개선이다. 단일 관측의 감소율을 모든 파일·환경에 보장하지 않는다.

작은 파일 5개의 첫 동일 입력 비교 `performance-small5-001/performance-results.json`도 성공했지만, 이는 Protected View·종료 전 경고 복원·즉시 unsafe 표시 검사를 넣기 전 소스다. 당시 설정은 72,392.70→37,306.39ms, 해제는 68,096.93→40,589.61ms였다. 이 중간 결과를 최종 후보 성능으로 사용하지 않는다.

최종 소스의 `performance-small5-final/performance-results.json`은 작은 파일 5개의 동일 입력을 다시 순차 비교했다. 설정 입력은 합계 30,920바이트, 해제 입력은 합계 84,480바이트다. 큰 파일 시험과 같이 작업별 기존·후보의 입력 해시가 일치하며 작업·runtime별 관측은 각각 1회다.

| 작은 파일 5개 | 기존 방식 | 최종 안전 검사 포함 후보 | 관측된 시간 감소 |
|---|---:|---:|---:|
| 암호 설정 | 68,633.88ms | 37,985.92ms | 44.65% |
| 암호 해제 | 67,396.71ms | 38,767.95ms | 42.48% |

네 실행 모두 성공했고 원본 백업·결과 해시·중간 파일 정리·Excel 종료를 포함한 98개 확인이 통과했다. 큰 파일의 34개 확인도 모두 통과했다. 두 최종 비교의 runtime 4개 해시가 현재 소스와 일치함을 대조했다. 이 수치는 해당 합성 자료와 한 환경의 단일 관측이며 보장 시간·최소 개선율이 아니다.

후속 안전 검사는 일반 통합문서뿐 아니라 Protected View 창도 0개인지 확인하고, Quit 직전에 경고 표시를 복원한 뒤 열린 문서를 다시 확인한다. 불확실 상태는 즉시 `unsafe.json`으로 표시하며 엔진은 커밋 전에 이 표시를 검사한다. 최종 worker 35확인, 세션 19조건·180확인과 전체 형식 Excel 회귀 31개는 통과했다. VBA는 전체 컨테이너 해시가 달랐지만 별도 정적 비교에서 내부 OLE 스트림 13개와 추출 소스 5개가 같았다. 이 결과를 전체 컨테이너의 바이트 동일성이나 매크로 실행 보장으로 확대하지 않는다.

## 진행 상태

최종 로컬 빌드는 `artifacts/excel-password-safe/build-3.0.0-20261117-091301-323da3f2`다. `-SkipTests`는 패키지 제작에만 사용했고 `build-result.json`의 `tests=NotRun`을 유지한다. 앞의 개별 엔진·세션·실제 Excel 근거와 아래 최종 EXE 검사를 별도로 연결하며 전체 suite를 빌드 안에서 실행했다고 표시하지 않는다.

이전 `085808-b70fbff6` 빌드(MSI SHA-256 `C9A632AA90F29C6C54755F3E7324E762DCD4E68050440580836483EEDF77C76F`)는 최종 게시 자산에서 제외했다. 마지막 diff 검사에서 `Test-WorkerSession.ps1`의 불필요한 파일 끝 빈 줄을 정리했고, 후속 `091040-33b1c218` 후보에서는 Windows PowerShell 콘솔을 상속하는 App 시험 실행이 `Exception.ToString` 오류로 실패했다. 같은 컴파일된 시험을 분리된 `Start-Process`로 실행한 42개 확인은 통과해 실행기 문제를 좁혔다. `Test-App.ps1`에 Wizard 시험과 같은 표준 출력·오류 명시 전달 방식을 적용한 뒤 최종 EXE에서 DPAPI 연동을 포함한 43개가 통과했다. 앞 실패를 성공으로 덮어쓰지 않는다. 제품 C#·runtime 소스는 이 과정에서 바꾸지 않았고, 최종 내장 runtime 바이트가 실제 Excel 회귀·성능 측정 자료와 같음을 확인했다.
