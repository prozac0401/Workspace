# ExcelPasswordSafe 5 · 백업·검증을 유지한 추가 지연 개선

기록 시작: 2026-11-17 · 버전: 5 · 상태: 구현·같은 입력의 전체 시간·최종 패키지 관련 검증 완료, 릴리스 준비
관련: [사용자 원문](../tools/excel-password-safe/original-request.md), [현재 명세](../tools/excel-password-safe/specification.md), [버전 4 직접 처리 기록](excel-password-safe-single-file-20261117.md), [ADR-0042](../design/0042-excel-password-safe-direct-ooxml.md)

## 요구와 필요한 완료 근거

사용자는 “작은 파일 하나에 4~5초도 아직 긴 것 같아요. 백업과 검증은 유지하면서 처리 시간을 더 줄일 수 있나요?”라고 요청했다. 작은 단일 파일의 실제 처리 시간을 추가로 줄이되 백업·암호/내용 검증·원본 보존 계약을 유지하는 것이 범위다.

기준 소스는 버전 4의 `a7606ac82de9c7cbc144ed893c0a1c6a91c81672`다. 버전 4의 합성 파일 6,184바이트 설정 4,326.32ms, 같은 Office 암호문 16,896바이트 해제 4,954.65ms는 앞 기록의 각 1회 관측이며 이번 작업에서 새로 측정한 값이 아니다. 사용자가 별도 파일·크기·구간별 시간을 제공한 것으로 해석하지 않는다.

우선 UI 실행 직후부터 엔진 시작·요청/백업·암호 계산·검증·교체·정리·UI 결과 표시까지 구간을 구분한다. 계산 구간만 빨라졌다는 이유로 사용자가 기다리는 전체 시간이 줄었다고 주장하지 않는다. 같은 입력·작업·조건의 전후 전체 시간, 선택한 변경에 직접 연결되는 회귀와 기존 불변 소스 근거가 확보되면 완료한다. 미래의 사용량을 위한 상주 프로세스·대규모 엔진 재작성·전역 암호 캐시는 먼저 도입하지 않는다.

## 유지할 불변조건

아래는 현재 `Engine.ps1`, `DirectCrypto.cs`, `PackageGuard.cs`, `WizardWindow.cs`와 명세를 읽어 정리한 변경 경계다. 특정 최적화의 채택이나 시험 완료를 뜻하지 않는다.

| 경계 | 줄이지 않을 검증·행동 |
|---|---|
| 승인과 범위 | 선택 경로/해시, 로컬 NTFS·재분석/읽기 전용/잠금 제외, 사용자별 중복 실행 방지와 기존 Excel 차단 유지 |
| 원본·백업 | 쓰기를 막은 원본 핸들과 승인 해시, private 실행 폴더, 백업 Flush(true)·실제 백업 해시, 처리 입력 복사본의 해시 유지 |
| 암호 강도 | 지원 알고리즘·key/salt 크기·KDF 반복 수와 무작위 생성 유지. 속도를 위해 반복 수나 파생 함수를 약화하지 않음 |
| 입력과 출력 검증 | 현재 암호와 전체 EncryptedPackage HMAC, 새 암호 재복호화·전체 평문 bytes 동일성, 잘못된 암호 및 변경의 이전 암호 거절 유지 |

| 검증한 결과 고정 | 출력 bytes의 해시를 기록 전에 고정, 새 temp를 독점 핸들로 기록·Flush(true)·실제 저장 해시 확인. 나중에 읽은 변조 bytes를 새 기준으로 승인하지 않음 |
| 교체 | 입력 복사본·원본 경로/잠긴 스트림·백업·temp 재확인, 취소/전달된 소유 상태, CommitIntent·File.Replace·결과/recovery 해시·Committed 유지 |
| 실패·정리 | 교체 전 원본 불변, 불확실한 교체는 재시도/자동 롤백 금지, 원본 백업 유지. 소유 임시/암호 전달 자료만 정리하고 실패를 숨기지 않음 |
| 비밀과 수명 | DPAPI 전달, 평문 명령줄/로그 금지, 요청 종료 시 정리 유지. 파생 계산을 재사용해도 다른 암호·salt·hash·spin·작업의 상태가 섞이지 않고 작업 밖 비밀 캐시를 추가하지 않음 |
| 사용자 결과 | 실제 엔진 종료와 최종 결과 검증 후 완료 표시. 진행 폴링을 줄이면서 성공을 앞당겨 표시하거나 취소/실패를 누락하지 않음 |

`WizardWindow`의 작업 완료는 비동기 실행 안의 `Process.WaitForExit()` 이후 결과 읽기로 이어진다. 진행 화면의 폴링 간격만으로 전체 완료 지연을 설명할 수는 없으며, 실제 결과 표시 구간을 별도로 측정해야 한다. 엔진과 codec에 반복 해시나 파생 호출이 있다는 사실도 비용의 크기를 계측하기 전 병목이라고 단정하지 않는다.

## 변경 지점에 맞춘 최소 검증

실제로 바뀐 행에 필요한 시험만 선택한다. 기존 암호 primitive·컨테이너·guard가 같다면 버전 4의 실제 Excel 225개 확인을 그대로 다시 실행하지 않는다. 반대로 암호 bytes 또는 COM 분기가 달라지면 그 차이에 직접 연결되는 상호운용 자료를 확인한다.

| 실제 변경 후보 | 필요한 회귀 | 그대로일 때 재사용할 근거 |
|---|---|---|
| 해시/KDF 실행 비용 | 같은 입력·Unicode·salt·spin·key/hash 조합의 기존/후속 파생 결과 동일성, 취소/오류, 양성 재복호화·부정 암호·HMAC 변조 거절. 구간과 전체 시간 구분 | 바뀌지 않은 ZIP guard 48개 및 컨테이너 분기. 같은 암호 bytes를 입증한 경우 기존 전체 상호운용 범위 |
| 요청/프로세스 준비 | 기존 DPAPI·경로 인수·실행 권한/환경, 단일 인스턴스·원본 해시·백업·취소·정리, 기존 host/fallback 동작. 실제 시작→완료 구간 | 변경하지 않은 codec 124개와 실제 Excel 결과 |
| 결과 통지·진행 갱신 | 성공/실패/취소/누락·불완전 결과가 올바른 마지막 단계로 연결, UI 스레드 막힘 없음. 변경된 화면이 있다면 해당 렌더 | 암호·원본 교체·MSI 수명주기 등 무관한 검증 |
| 백업·검증·교체 호출 순서 | 해시/잠금/백업/출력 변조·교체 전 취소·교체 불확실·정리 실패에 직접 연결되는 제어기 회귀 | 변경하지 않은 암호 primitive/화면/설치 |

실제 전후 비교에서는 최종 후보 소스/바이너리 해시, 같은 평문/암호문 입력 해시, 실행 순서·횟수·부하 조건을 기록한다. 처음 실행의 프로세스/JIT 비용과 반복 실행을 섞어 최소값만 대표 시간으로 택하지 않는다. 계측 코드와 독립적인 전체 시간 비교를 구분하며 실패·취소·시간 초과를 성공 표본에 넣지 않는다.

## 조사 결과와 채택한 구현

`artifacts/excel-password-safe/kdf-poc-001/kdf-results.json`은 합성 암호·salt로 같은 SHA-512 100,000회 파생 계산을 비교했다. 후보별 3회 중 중앙값은 기존 codec 637.045ms, 작업 안에서 재사용하는 Windows BCrypt 62.891ms였다. 매번 만드는 CNG 402.917ms, CSP 42,348.187ms, 중간값을 지우며 재사용하는 managed 구현 254.262ms도 함께 보존했다. 모든 표본의 결과 bytes가 기존 구현과 같았고 취소 5개 확인이 통과했다. 이 자료는 KDF 구간 비교이며 파일 전체 처리 시간이나 새 제품의 완료 근거가 아니다.

이를 근거로 네이티브 해시 객체를 한 번의 파생 계산 안에서만 재사용하는 구현을 선택하고 전체 시간 검증 뒤 버전 5에 채택했다. 기존 반복 수·입력 순서·결과 bytes와 양성/부정 검증은 유지한다. 고정된 upstream 파일은 변경하지 않고 빌드 출력의 사본에서 legacy 파생 호출 하나만 연결한다. 포인터 수명·네이티브 반환 상태·비밀 버퍼 정리·취소와 원본 해시 검증을 독립 코드 검토 및 표적 시험으로 확인했다.

구현 검토에는 Microsoft의 [재사용 해시 절차](https://learn.microsoft.com/en-us/windows/win32/seccng/creating-a-hash-with-cng)와 [BCryptCreateHash의 객체 버퍼 수명](https://learn.microsoft.com/en-us/windows/win32/api/bcrypt/nf-bcrypt-bcryptcreatehash)을 기준으로 사용한다. 결과가 같다는 시험만으로 네이티브 메모리 소유권이 안전하다고 간주하지 않는다.

초기 읽기 검토에서 native 생성 성공 직후 관리 owner 할당이 실패하면 아직 참조 중인 버퍼를 해제할 수 있는 경계를 발견했다. 구현은 owner를 먼저 만들도록 수정했고, 수정본에서 객체 생성 실패·정리 실패·취소 시 결과를 반환하지 않으며 버퍼를 DestroyHash 성공 후에만 해제하는 흐름을 재검토했다. 이 항목은 코드 검토 기록이며 실행 시험 PASS를 대신하지 않는다.

`profile-v4-001/profile-results.json`은 계측용 사본의 구간 자료다. startup UTC가 계측 목록 초기화 뒤에 잡혀 시작 비용은 근사값이며, 구간 합계를 정확한 전체 시간으로 취급하지 않는다. 제품에 이 계측 코드를 넣거나 이 자료를 독립적인 전후 성능 결과로 쓰지 않는다. 별도의 PowerShell host·assembly 로더 후보는 실제 전체 처리에서 이득을 확인하지 못해 채택하지 않았다. 기존 엔진·프로세스 실행 방식은 유지한다.

전체 시간 하네스는 mode별 동일한 불변 입력으로 기존/후속 순서를 바꾸며 기본 3쌍을 실행한다. 타이머는 `Start-Process` 호출 직전부터 종료 관측까지이며 요청 준비·독립 사후 검증을 제외한다. 백업·교체·정리를 포함하고, 타이머 밖에서는 실제 로드된 DLL 해시를 확인한 기존 codec으로 전체 평문 해시를 다시 확인한다. 암호문 입력은 이번 하네스의 기존 codec이 만든 고정 입력이므로 버전 4 기록의 Office 생성 암호문과 같은 입력이라고 주장하지 않는다.

## 같은 작은 파일의 전체 시간

각 mode에서 1·3회는 기존→후속, 2회는 후속→기존으로 순서를 바꿨다. 평문은 6,184바이트, SHA-256 `CB3B4920A17BA8835FDA128EC3815D92B7A60D6EA0FD239D267F089AC4FD38FA`다. 해제·변경 입력은 같은 10,240바이트 암호문, SHA-256 `8EBD1AF2372A4F096FBEB2FC073B69AAAA18756C6C5B2E0565B7E463F7084170`이다. UI 암호 입력 시간은 포함하지 않는다.

| 작업 | 기존 중앙값 ms | 후속 중앙값 ms | 기존 최소–최대 ms | 후속 최소–최대 ms |
|---|---:|---:|---:|---:|
| 설정 | 4,445.45 | 3,612.45 | 4,246.81–7,242.23 | 2,857.07–3,877.23 |
| 해제 | 3,763.67 | 3,034.57 | 3,494.86–4,396.04 | 2,890.06–3,189.93 |
| 변경 | 6,647.88 | 3,608.46 | 6,405.97–7,402.77 | 3,548.81–3,656.83 |

표는 한 PC에서 같은 작은 합성 파일을 작업별 3쌍씩 비교한 관측이다. 설정·해제의 전체 시간은 여전히 약 3초대이며 KDF 구간의 개선 비율만큼 전체 시간이 줄었다고 해석하지 않는다. 다른 PC·파일·첫 실행의 보장 시간은 아니다.

기존 DLL SHA-256은 `E5629EDF466C6A4D972CB37226CACC54989092C0B74BB9AC91AF76E3EBAC6301`, 후속 preview DLL은 `683FF1C9154FC5ABB1A95938B7DD43831E78ECCAD14EB34A99FADFDF9F6B5642`다. 비교한 4개 PowerShell 런타임 파일의 bytes는 동일하다. 후속 preview의 Assembly 버전 메타데이터는 아직 `4.0.0`이었고 제품 코드 검증 뒤 표시 버전 `5`를 채택했다. 최종 5 패키지는 버전 메타데이터를 바꾸므로 DLL 해시가 달라진다. 최종 소스 대조와 직접 codec·표적 상호운용 결과로 패키지에 연결하며 이 preview 측정을 최종 MSI 자체를 실행한 시간으로 표시하지 않는다.

REQ-EPS-026은 같은 입력의 전체 시간 감소와 백업·검증 유지로 대응한다. REQ-EPS-002~004·006·008·016은 기존 검증 호출·엔진 유지, 네이티브/오류/codec 회귀 및 각 측정의 백업·교체·정리 확인으로 연결한다.

## 최종 패키지와 재사용한 범위

최종 빌드는 `build-5.0.0-20261117-230517-4db0dda0`다. `-SkipTests`로 패키지를 생성했으므로 빌드 기록의 tests=NotRun을 유지하고 위의 별도 실행 근거와 구분한다. MSI의 9개 payload 추출 해시, HKCU 6개 메뉴 루트·18개 명령, 사용자 지정 설치 경로의 정적 확인은 PASS다.

| 파일 | 크기·SHA-256 |
|---|---|
| `ExcelPasswordSafe-5-win-x64.msi` | 253,952바이트 · `23F807B96AF77FFF47450A4B1E7D63EF78566650D0AB767FA6971D922B3D2B72` |
| `ExcelPasswordSafe.Crypto.dll` | `D0A846DBDD87269E05F918D2552E2264C811623DE709B2D5622F74F8EE36982B` |
| `ExcelPasswordSafe.exe` | `5C5B128835A3928998FC4656BC49CA3343387A92FE71CE1FB23B13F0D33367C0` |

preview와 최종 빌드의 crypto 컴파일 입력 27개 해시가 같고 버전 메타데이터만 4→5로 바뀌었다. 전체 시간 비교를 반복하지 않고 최종 DLL의 47·59·124개 회귀와 실제 Excel의 표적 56개 확인으로 최종 산출물을 연결했다. 변하지 않은 PackageGuard·컨테이너 범위와 PowerShell 제어기·WPF 흐름의 기존 근거는 [버전 4 기록](excel-password-safe-single-file-20261117.md)에서 범위를 확인한다. 이를 버전 5에서 전체 225개 Excel·전체 UI·전체 설치 시험을 새로 수행한 것으로 합산하지 않는다.

첫 MSI `19CFB739…B637`은 설치본 README의 상대 문서 링크를 tag의 절대 링크로 고치면서 교체한 후보이며 최종 배포 파일이 아니다. 제품 암호 코드와 성능 측정에는 이 안내 링크 변경이 영향을 주지 않는다. 이 후보 및 `.generated.cs` 이름에서 발생했던 nullable 컴파일 문제, 첫 시간 하네스의 오류 기록은 로컬 증거로 보존한다.

서명 상태는 `NotSigned`다. 이번 버전의 실제 MSI 설치 수명주기·탐색기 클릭·실제 GUI 작업 시험은 NOT RUN이며 코드 변경과 직접 관련 없는 기존 검증을 반복하지 않았다. 최종 화면 60개 렌더는 위 표처럼 별도로 실행했다. 1.2.0에서 발견한 늦은 MSI rollback의 제품 등록 잔존 제한을 해결했다고 주장하지 않는다. 설치 실패 뒤 앱 항목만 남거나 재설치 메뉴가 없으면 같은 MSI로 제거한 뒤 재설치하는 안내를 유지한다. 정적 패키지 PASS는 서명·상용 승인·실제 메뉴 실행의 증거가 아니다.

릴리스 준비 자료와 게시를 구분한다. 태그 `excel-password-safe-v5`의 실제 공개 상태·다운로드 파일은 [GitHub 릴리스](https://github.com/prozac0401/Workspace/releases/tag/excel-password-safe-v5)와 별도 게시 기록에서 확인한다. 소스 ZIP 자체의 해시나 게시 완료를 소스에 선기입하지 않는다.
