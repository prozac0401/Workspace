## 요청과 완료 기준

사용자는 MSI 설치 위치 선택, 평가용 문구 제거, 정수 버전 2, 자물쇠 아이콘, 탐색기 빈 공간의 현재 폴더 메뉴, 작은 단계형 화면과 사람에게 자연스러운 사용 흐름을 요청했다. 완료 후 릴리스도 명시적으로 승인했다.

검증 범위는 진입점별 단계·필수 입력·오류 수정·진행·결과·안전한 수동 재시도, 작은 화면과 아이콘, 설치 위치 선택·유지·제거, 실제 탐색기 빈 공간과 최종 설치 앱이다. 암호 엔진은 원본 패키지와 비교해 기존 근거를 승계했다. 완료한 자동 검사와 직접 입력 검사는 아래에 기록하고 미실행 범위와 구분한다.

사용자는 이후 “우선 릴리즈 해주세요. 사용해보고 추가 피드백 드리겠습니다”라고 명시했다. 이에 현재 검증된 최종 MSI를 변경하지 않고 우선 릴리스한다. 남은 실제 GUI 검사를 통과로 바꾸지 않으며 실사용 피드백을 받는다. 이 기록은 게시 전 준비 상태이며 실제 GitHub 자산 확인은 별도 게시 기록에 남긴다.

## 독립 UX 검토

문맥 메뉴에서 고른 작업을 다시 선택하거나 모든 입력과 큰 표를 항상 표시하던 부담을 줄인다. 입력 옆 오류와 필요한 칸의 초점, 명확한 작업 버튼·뒤로, 완료 뒤 보고서·기록·다음 행동을 연결한다. 안전한 실패만 재시도하고 성공한 파일은 제외한다. 별도 동의 체크·확인 페이지만을 위한 단계를 두지 않되 원본 교체·백업 안내와 명시적 실행은 유지한다.

빈 최종 JSON을 완료처럼 표시할 수 있던 경로는 독립 검토에서 발견해 최종 상태·대상 경로·파일별 결과의 완전성을 검사하도록 수정했다. 중간 진행만으로 완료를 판정하지 않고 손상·누락 결과는 기록 확인으로 안내한다. 해당 순수 규칙 43개 시험을 통과했다. 암호 기본 마스킹, 뒤로·실행·결과의 초기화, 성공 파일 제외와 불확실 상태의 재시도 차단을 코드로 대조했다.

기본 작업 선택의 불필요한 스크롤과 버튼의 부가 설명을 없애는 후속 요청을 반영한다. 실제 UIA Description에서 대상 전체 경로가 노출됨을 확인했다. 최종 코드·렌더·실사용 결과는 각 근거로 구분한다. 디자인을 개선했다는 이유로 접근성 인증·모든 사용자 환경·상용 인수가 완료됐다고 주장하지 않는다.

이어 사용자는 문맥 메뉴에서 이미 작업을 골랐음을 다시 지적했다. 이에 파일 메뉴도 세 작업을 펼치는 구조로 바꾸고 파일·선택 폴더·빈 공간 모두 최소 암호 입력으로 바로 진입하도록 확정했다. 문맥 입력의 취소는 닫기이며 결과의 다른 작업은 숨긴다. 일반 실행과 이전 작업 인수 없는 파일 호출의 선택 흐름은 유지한다. 최초 후보의 기존 파일 메뉴 검사와 최종 후보의 새 메뉴 검사를 섞지 않는다.

드라이브 루트의 빈 공간 인수도 별도로 재현했다. 기존 `"%V"` 형태는 `D:\` 끝의 역슬래시 때문에 닫는 따옴표가 이스케이프되어 작업 인수가 합쳐졌다. `"%V\."` 전달과 UI의 절대 경로 정규화로 수정했다. `argv-root-002/argv-results.json`은 드라이브 루트·공백 있는 일반 폴더 2조건에서 실제 .NET Framework 프로세스의 정확한 인수 4개와 원래 경로로의 정규화 4확인 PASS다. 초기 실패 근거 `argv-root-001`도 보존한다. 이는 인수 회귀 검사이며 실제 탐색기 클릭·Excel 처리는 별도다.

## 이전 근거와 제한

[1.4.0 폴더·재시도 검증](excel-password-safe-folder-20261116.md), [1.3.0 UI 검증](excel-password-safe-ui-20261116.md), [1.2.0 엔진 검증](excel-password-safe-20261116.md)을 당시 기록으로 보존한다. 이전 검사 수를 이번 실행 수로 합산하지 않는다.

원본 1.4 MSI SHA-256 `99927E93B153D6DDA478C41AF0F26A5AFDB9ADEFA3FEC80E289FB7943A34D029`를 새로 추출해 비교했다. `Common.ps1`, `Engine.ps1`, `ExcelPassword.Worker.ps1`은 바이트와 SHA-256이 같다. `BatchEngine.ps1`은 기존 LF 270행과 현재 CRLF 270행 차이이며 UTF-8 BOM은 같고 CRLF를 LF로 바꾼 뒤 전체 바이트가 같다. 따라서 동작 소스의 연속성은 확인했지만 런타임 4개 모두의 원시 해시가 같다고 표시하지 않는다.

기존 늦은 MSI 실패 주입에서 파일·메뉴가 제거돼도 제품 등록이 남았던 제한은 이번 변경으로 해결됐다고 표시하지 않는다. 같은 MSI로 제거 후 재설치하는 안내를 유지한다. 실제 서명 결과는 이 기록에 남기며 사용 안내의 평가용 문구 삭제는 코드 서명·조직 승인·상용 적합 판정이 아니다.

원본 백업에는 암호 없는 자료가 남을 수 있다. 파일 내용 검증은 모든 그림 픽셀·삽입 개체·매크로 동작·외부 연결의 동일성 보장이 아니다. 실제 환경과 확인한 작업을 기록하고 다른 조합으로 일반화하지 않는다.

## 산출물과 게시

최종 빌드 근거는 `artifacts/excel-password-safe/build-2.0.0-20261117-071013-dc0fce4d`다. MSI는 `ExcelPasswordSafe-2-win-x64.msi`, 200,704바이트이며 SHA-256은 `D25D849687F2D90F483E86ADC10F461DA64DCD775552ABF30BB080A491006C53`다. 최종 EXE SHA-256은 `FE1E1ABD0584963610029AF8484DD8CC53C6FE9A3FAFD4D51F3B156F2A334B4A`다. 추출한 설치 파일 7개의 해시가 staging과 일치했다. 메뉴는 파일 12개·선택 폴더 3개·빈 공간 3개, 합계 18명령·6루트이며 HKCU만 사용한다.

최종 빌드는 `SkipTests`로 패키지를 만들었으므로 `build-result.json`의 `tests=NotRun`을 그대로 보존했다. 이후 같은 최종 EXE로 새 App·Wizard·60렌더를 실행한 `postbuild-verification.json`과 기존 엔진 근거 승계를 별도로 연결한다. 이전 화면·10명령 후보 MSI는 최종 산출물로 사용하지 않는다.

자체 문서를 포함한 소스 ZIP의 해시는 ZIP 옆 파일과 별도 게시 기록에 둔다. 원시 진단·개인 경로·사용자 기록·업무 파일은 공개 자산에 포함하지 않는다. 소스·패키지·시험·게시 결과를 구분한다.

이 기록은 릴리스할 소스와 ZIP에 포함되므로 게시 이전의 준비·검증 상태를 고정한다. 예정 태그는 `excel-password-safe-v2`이며 실제 릴리스 ID·대상 커밋·업로드 자산·공개 다운로드 해시는 게시 이후의 별도 기록과 GitHub 릴리스에서 확인한다.
