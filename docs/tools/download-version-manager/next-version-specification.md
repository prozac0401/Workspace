결정일: 2026-10-04 KST · 제품 책임: 개발 담당 · 결정 근거: 사용자의 폴더 감시 전환·입력 규칙 확인·MSI 릴리즈 지시

정책: [추가 도구 개발 기준](../../policies/tools.md), [문서 작성 규칙](../../policies/documentation.md) · 설계: [ADR-0028](../../design/0028-download-version-manager-folder-input.md) · 이전 버전: [0.1.0 원본 명세](specification.md)

## 최우선 원칙

**각 구현 단계에서 과도한 테스트와 확인된 요구 없이 선제적으로 복잡도를 늘리지 않는다.** 확인된 동작과 실제 파일·설치 위험을 판단할 최소 검증만 수행한다. 기존 성공 근거를 재사용하며 실제 FAIL/NOT RUN을 보존한다.

0.1.0은 미완료 평가 버전으로 보존한다. 이번 사용자 지시는 0.2.0의 구현부터 실제 설치·구동 가능한 단일 MSI 릴리즈까지다. 명세 작성만으로 설치·게시 완료를 선언하지 않는다.

## 사용자와 목적

브라우저나 웹 프로그램의 종류와 관계없이 지정 폴더에 들어오는 파일을 감지한다. 확인된 같은 이름 규칙의 신규 파일 자체가 원래 이름을 갖고, 바이트가 다른 이전 내용만 그 폴더의 `_history`에 보관한다. 브라우저 확장이나 스토어 설치는 필요하지 않다.

## 이름·완료·최신의 입력 계약

처음 감시할 폴더를 사용할 때, 파일명·수정 시각·크기와 같은 이름 규칙의 그룹을 보여준다. 수정 시각과 suffix 번호는 참고 정보다. 사용자가 번호 파일을 최신으로 선택하면 전체 그룹의 처리 순서를 보여 주고 `선택대로 정리`를 눌렀을 때만 실행한다. 나머지 번호 파일은 표시된 파일명 순서로 처리하고 선택한 파일을 마지막에 처리한다. 매 단계에서 직전 원래 파일은 내용이 다르면 History, 같으면 삭제한다.

원래 이름의 파일을 선택하거나 `이 그룹 보존`을 누르면 그 그룹 전체를 현재 이름 그대로 보존한다. `남은 그룹 모두 보존`도 가능하다. 창을 닫아 검토를 취소하면 감시를 시작하지 않는다. 미리보기 이후 파일이 바뀌거나 처리 단계가 실패하면 해당 그룹의 남은 파일을 보존하고 멈춘다. 이 확인은 최초 감시 또는 선택 폴더 변경의 경계이며 로그인마다 기존 파일을 자동 정리하지 않는다.

이후에는 같은 폴더의 기존 대상이 있고 파일명의 마지막 ` (n)`이 양의 정수인 새 파일을 대상으로 연결한다. 이 규칙은 사용자가 채택한 이름 관례이며 실제 다운로드 출처나 원래 사이트 파일명을 증명하지 않는다. 원래 이름 자체가 `(1)`인 별개 문서도 이 규칙에 맞으면 처리될 수 있으므로, 이런 파일을 별개로 다루는 폴더에는 감시를 적용하지 않는다.

3초 동안 관찰한 객체·크기·쓰기 시각이 바뀌지 않고 처리 핸들을 확보할 수 있으면 처리한다. 이는 **앱이 다운로드를 완료했다는 증명은 아니다.** 느린 쓰기의 긴 중단이나 완료 후 다시 쓰는 앱까지 보장하지 않는다. 신규 객체는 처리 직전 잠금 핸들에서 관찰값을 다시 대조한다.

브라우저 `endTime`을 사용하지 않는다. 단일 후보가 처리 가능해진 시점의 신규 유입을 최신으로 받아들인다. 같은 원래 대상의 후보가 함께 대기하면 모두 보존하고 해당 감시 세션의 그 대상 자동 처리를 보류한다. 사용자가 파일을 직접 확인한다.

## 범위와 금지 동작

선택 폴더의 바로 아래만 감시한다. `_history`, 내부 `.dvm-…pending`, Office 임시 파일과 알려진 다운로드 임시 확장자는 처리하지 않는다. OS 폴더 변경 알림을 사용하며 반복 전체 스캔·전체 디스크 탐색·재귀 정리를 추가하지 않는다. 최초 이름 그룹 확인은 선택 폴더의 이름·파일 정보만 읽고 실제 비교는 승인된 source/target 두 객체로 제한한다.

직접 덮어쓴 이전 바이트의 사후 복구, 앱 내부 DB·드라이버·서비스·앱별 연동·범용 규칙 엔진·restore UI·클라우드 전송·telemetry·자동 업데이트는 범위 밖이다. Windows 11 x64의 고정 로컬 NTFS를 대상으로 하며 UNC·네트워크·reparse·클라우드 연결·ARM64 지원은 선언하지 않는다.

## 동시 실행과 복구

프로그램은 사용자 세션당 하나이며 동일 대상의 파일 변경에는 기존 mutex를 사용한다. 폴더 입력은 기존 브라우저용 `CompletionOrder` 상태를 읽거나 수정하지 않는다. 기존 경로·잠금·비교·History 충돌 처리와 rollback을 재사용한다.

이전 파일 이동 후 신규 이름 이동이 실패하면 이전 파일 복구를 시도한다. 강제 종료·전원 장애의 자동 재생이나 잔재 일괄 정리는 없다. 이전·신규 객체를 남긴 위치에서 직접 확인한다. 알림 누락이나 후보 한도 초과 시 감시를 중지하고 보존한다.

## 설정과 설치·제거

네이티브 C++ x64, 정적 CRT(`/MT`), Windows API로 제작한다. 제품 버전은 새 빌드의 0.2.0이며 기존 `version.json`의 0.1.0 / protocol 2와 기존 빌드 경로는 역사적 구현으로 보존한다.

`DownloadVersionManager-Watcher-0.2.0-x64.msi` 한 파일을 일반 사용자 LocalAppData·HKCU에 설치한다. 설치 경로와 MSI 제품/upgrade 식별자를 0.1.0과 분리하고 구버전 설치·브라우저 등록·순서 상태를 자동 이행하거나 삭제하지 않는다. 로그인 자동 실행은 기본 선택이며 위자드에서 해제할 수 있다. 프로그램 창을 닫으면 현재 감시는 종료한다.

기본 위치는 하드코딩한 `Downloads`가 아니라 Windows `FOLDERID_Downloads`를 해석한다. OS가 관리하는 리디렉션·환경 변수 포함 위치를 반영한다. 기본 위치 추종을 선택한 경우 앱 시작과 User Shell Folders 변경 알림에서 다시 해석하고 감시 폴더를 전환한다. 새 위치의 첫 이름 그룹 확인도 거친다. 직접 고른 사용자 폴더는 Windows 다운로드 위치 변경과 무관하게 유지한다.

제거는 프로그램과 제품이 소유한 설치 등록·선택한 시작 항목을 대상으로 한다. 감시 폴더 파일·History와 사용자 실행 설정을 보존한다. 코드 서명은 없으며 조직의 도입·상용 승인 여부는 미결정이다.

## 검증·배포 상태

폴더 엔진 8건·OS 알림 watcher 대표 세션 15건·최초 그룹 처리 4건은 PASS다. production 제작·MSI 구조와 문서 strict·공개 링크, 수정 후보의 설치/실행·repair·제거·파일 보존 5건, 화면 높이 수정 후보의 설치/실행·제거·보존 4건도 PASS다. 실제 위자드의 현재 기본 위치·체크·취소를 확인했다. 최종 안내 문구 수정에는 관련 설치 근거를 재사용했다. 표준 MSI 폴더 선택의 경로 표시·설정 전달·취소는 최종 파일에서 별도로 확인했다. 새 MSI late-failure에서 제품 등록 rollback 실패는 남으며 공개 tag·Release·두 자산 다운로드·checksum은 PASS이며 다음 로그인·실행 중 OS 위치 변경은 NOT RUN이다. [실제 시험 기록](../../../tools/DownloadVersionManager/TEST_RESULTS.md)과 [이번 배포 기록](../../delivery/download-version-manager-watcher-release-20261004.md)에 후보 지문·한계를 구분한다.

0.1.0의 Win11 rollback access denied(5)·재설치 1638·`installerFailureRecovery FAIL`, 단일 배포 FAIL, 브라우저 NOT RUN은 당시 판정으로 보존한다. 다른 MSI 식별자와 간소화된 새 구조만으로 과거 실패가 해결됐다고 판단하지 않는다. 새 설치 구조의 관련 실패 복구를 확인한다. 확장/Store 전용 관문과 과거 전체 시험표는 0.2.0에 복제하지 않는다.

## 0.2.1 후속 계약과 검증 기록

위 0.2.0 원본 명세와 최우선 최소 구현·검증 원칙은 보존한다. 아래 기록은 2026-10-05~06의 후속 계약과 실제 결과를 날짜별로 옮긴 것이다. 당시의 현재 설치본·공개 파일·FAIL/NOTRUN은 그 시점의 의미로 유지하며 최신 0.2.1 판정은 마지막 절을 따른다.

후속 설계: [ADR-0031](../../design/0031-download-history-mtime-guidance.md), [ADR-0032](../../design/0032-download-version-manager-tray-lifetime.md). 2026-10-06 사용자는 검증한 정상 MSI를 재빌드 없이 재사용하는 정식 Release와 Pages 게시를 승인했다. 실제 게시·다운로드·checksum 확인은 준비 및 로컬 검증과 별도로 기록한다.

### 2026-10-05 후속 사용자 결정

2026-10-05 사용자가 새 History 이름의 날짜를 실제 보관 대상의 마지막 수정 시각으로 바꾸고 파일 보존 이유를 쉽게 알리도록 확인했다. 아래 후속 요구는 로컬 소스 개선에 적용한다. 공개 0.2.0 MSI와 현재 설치본은 보관 작업 시각 규칙이며 이번 변경을 반영하지 않았다. 설치 복구 검증은 승인된 격리 Windows 환경이 없어 **BLOCKED**이며 날짜·안내 개선과 별도로 유지한다.

2026-10-05 후속 사용자 요청은 원래 처리 기능을 유지한 상용 품질 수준의 UX 개선과 **로컬 MSI 제작**이다. 수정 EXE의 새 날짜 이름·읽기 전용 이유·긴 로그 수평 스크롤은 USER_CONFIRMED로 추가 기록했다. 기존 자동 63 PASS와 당시 UI NOTRUN은 역사적 결과로 보존한다. 로컬 MSI 제작 승인은 현재 설치본 변경이나 새 버전 공개 승인이 아니며, 후속 결과와 향후 복구 시험 조건은 [UX·로컬 MSI 기록](../../delivery/download-version-manager-ux-package-20261005.md)을 따른다.

2026-10-05 사용자가 새 카드 UI와 현재 동작을 확인했다(USER_CONFIRMED). 확인 범위는 해당 사용 사례이며 모든 환경·설치·복구·업그레이드의 PASS가 아니다. 이어 감시 창의 X·Alt+F4를 트레이 유지로 바꾸고 같은 창 복원·명시적 종료를 제공하는 최소 변경, 집중 시험과 새 로컬 EXE·무서명 MSI 제작을 요청했다. 버전·패키지 정책은 기존 로컬 0.2.1 후보를 따른다. 앞선 새 집중 17 PASS와 core 57 PASS·설치 진단 8 PASS 재사용은 당시 [UX 기록](../../delivery/download-version-manager-ux-package-20261005.md)의 근거로 보존하며 이번 트레이 변경의 새 PASS로 세지 않는다. 새 실행·미실행·산출물은 [트레이 작업 기록](../../delivery/download-version-manager-tray-20261005.md)에서 구분한다. 설치 실패 복구는 전용 격리 Windows 환경 미확보로 BLOCKED, 실제 복구 PASS 0을 유지한다.

## History 날짜와 보존 안내의 후속 계약

History 날짜는 보관하는 현재 시각, incoming이라는 역할 이름이나 생성 시각이 아니라 **실제로 이동하는 객체의 마지막 수정 시각**이다. 폴더 처리와 최초 그룹 처리에서는 직전 원래 파일이 대상이다. 공용 엔진의 역순 완료 요청 경로에서는 늦게 전달된 incoming 객체가 대상일 수 있으므로 같은 보호된 이동 핸들의 FILETIME을 사용한다. 마지막 수정 시각은 완료 순서나 최신본을 선택하는 기준으로 바꾸지 않는다.

PC의 해당 날짜 시간대·서머타임 규칙으로 로컬 시각을 변환하고 `YYYYMMDD_HHMMSS`와 `_001`, `_002` 충돌 회피를 유지한다. 초 미만 표시·반올림·고정 `+09:00`은 추가하지 않는다. 기존 10,000개 후보 상한과 덮어쓰기 없는 핸들 이동을 유지한다. 기존 History 이름을 정리하거나 이름에 맞추려고 보관 파일 시간을 다시 설정하지 않는다. 시각 조회·변환이 실패하면 이름·위치 변경 전에 `file_info_failed`와 Windows 오류를 남기고 보존하며 현재 시각으로 대체하지 않는다.

엔진이 파일을 보호해 연 시점에 읽기 전용 속성을 확인한 경우에만 내부 결과의 원인 표시를 전달한다. 표시 문구는 `읽기 전용 보호: 파일 보존`이며 다른 `permission_denied`는 `접근 실패: 파일 보존`이다. 이유를 파일명·상태·오류보다 앞에 두며 기존 경고와 복구 위치도 보존한다. 기존 상태 값과 Host JSON 응답 형식은 바꾸지 않는다. UI에서 나중에 속성을 다시 읽어 원인을 단정하지 않는다. 권한·속성 변경, 새 팝업·설정, 자동 재시도나 실패 큐 정책 변경은 없다.

탐색기의 충돌 선택 화면은 Windows 기본 UI다. DVM은 번호 파일이 생성된 뒤 감지하며 바로 덮어써 사라진 이전 내용을 사후 보관할 수 없다.

## 감시 창과 트레이의 후속 계약

감시 창의 일반 닫기 요청(X·Alt+F4)은 트레이 접근 경로가 확보됐을 때 기존 창을 숨긴다. 작업표시줄에 최소화 창을 남기는 방식으로 바꾸지 않는다. 감시 스레드·이벤트·타이머를 중지하거나 다시 만들지 않으며, 이미 중지한 감시도 임의로 시작하지 않는다. 초기 파일 그룹 확인 창의 닫기 취소 계약은 그대로다.

트레이의 **열기**와 아이콘 더블클릭은 같은 HWND를 복원하고 활성화한다. **종료**는 기존 안전한 감시 중지·스레드 대기와 창 파괴를 거쳐 프로세스를 끝내고 아이콘을 제거한다. 최소화 버튼·로그인 자동 실행·시작 시 창 표시·감시 시작 정책은 바꾸지 않는다. 새 설정·팝업·별도 감시 프로세스는 추가하지 않는다.

최초 등록 실패는 창을 숨기지 않고 기존 기록에 남긴다. Explorer의 TaskbarCreated 알림에서는 같은 창과 감시를 유지하며 아이콘을 재등록한다. 재등록 실패로 숨은 창에 접근할 수 없게 되면 창을 복원하고 실패를 기록한다. 기존 singleton의 두 번째 실행은 숨은 기존 창을 복원하는 경로를 재사용한다. Windows 로그오프·종료 요청은 일반 닫기와 구분하고 OS 종료를 숨김으로 바꾸거나 막지 않는다.

새 EXE 확인 전에는 기존 앱을 정상 종료하고 프로세스 종료를 확인한다. 트레이 수정본의 X는 완전 종료가 아니므로 트레이 **종료**를 사용한다. 이전 버전에 그 메뉴가 없으면 확인된 기존 정상 종료 경로를 사용한다. 기존 프로세스를 안전하게 종료할 수 없으면 정확한 새 EXE의 전체 시작 확인만 보류하며 빌드·payload 검사와 구분한다.
